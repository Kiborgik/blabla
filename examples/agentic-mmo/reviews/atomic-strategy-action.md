# Explicit atomic strategy and action

Actual author: gpt-6-astra/xhigh, 2026-10-16. Scope is the existing hosted action transport, repository transaction, focused tests and documentation. CLI paging is paused; the shared page module and core are unchanged.

## Deciding live problem and design

Aster observed revision156 at16:01:15 with civic research available. Its explicitly chosen civic-institutions command returned `strategy_catchup_required` by16:01:29 after crossing the next one-minute strategy boundary. The rejected command was not retried. This matches the other actors' observed upkeep→observation→action race; speeding up a perpetual root scheduler is not a reliable solution.

The registered draft `strategy-actions.bla` preceded implementation. The approved solution is an explicit wrapper through the existing authenticated `play_action` / `/api/action`: `action: {type:"strategy-action", action:<exact GameAction>}`. Strict revision matching and one request-captured server timestamp bind the candidate. At most sixty strategy beats are calculated in memory; only after complete catch-up does existing legal-action enumeration, admission and optional attached-plan validation inspect the exact inner action. No numeric selector, alternate city, offer, recipe or replacement action is chosen. The original observation revision is retained in an attached plan.

## Persistence and failure boundary

A successful due composite uses four statements in one existing atomic batch: upkeep history INSERT, action history INSERT, final world UPDATE, one action receipt INSERT. Both INSERTs and the UPDATE are guarded by the original world revision. The action row begins at the candidate upkeep revision; its ending revision is exactly one later. With no due beat the existing three-statement action batch suffices. The internal upkeep history key `strategy-before-action:<commandId>` cannot collide with the existing client operation namespaces. Both logical snapshots remain raw and retained; no deletion, compression writer or schema migration occurs.

Existing `strategy-catchup` and `action` transition shapes preserve deterministic replay. The upkeep provenance is system `clock-service`, seat5, null model, linked to the same private submitting identity; the action provenance records the real model, seat and original command ID. Public redaction is unchanged. One persisted response identifies the composite operation, accepted revision, actual strategy timestamp/start/end/tick count and zero remaining backlog. Existing private `action_receipt` readback recognizes that one action receipt. Original request fingerprinting excludes generated server time and includes the wrapper, inner action, plan and caller. Later identical retries return the original accepted result without rerunning upkeep; changed content conflicts.

Any action/plan/admission refusal, candidate terminal outcome, stale revision, losing CAS or database exception commits neither stage. A bound overflow also commits nothing and reports `processedTicks:0` plus the entire still-due backlog, not merely the candidate overflow. The caller must explicitly drain upkeep-only and reconsider. There is no blind CAS rebase for this opt-in composite; ordinary exact-action rebase remains unchanged.

The explicit upkeep-only alias is `action:{type:"strategy-catchup",timestamp:<observed UTC>}` with normal outer required fields and no plan/index. It reuses the existing strategy mutation and typed receipt namespace. The exact original envelope remains in its fingerprint. Its separate response discriminator is added at the transport return; the underlying persisted receipt/history remains the existing strategy operation. It does not spend a tactical action, including when no beat is due. The existing action-only readback does not claim to find upkeep receipts.

## Research and operational limit

The current official [D1 batch documentation](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), read2026-10-16, documents ordered statement execution with transaction rollback on statement failure. The implementation reuses the repository's established batch binding; local SQLite trigger tests establish this code's rollback behavior. This does not verify a new deployment or establish managed Sites quotas, peak memory, or an exact unattended wake schedule.

Storage cost is explicit: a due successful composite retains two full logical snapshots, just as two separately successful upkeep/action requests would; it has one receipt instead of two. Rejected candidates retain nothing. The sixty-beat cap bounds strategy work by count, not universal CPU or heap use. Idle worlds still require an explicit supported driver. Independent review and deployment/readback remain the next bounded acceptance steps.
