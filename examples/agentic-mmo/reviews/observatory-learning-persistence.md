## Exact persistence seam

Only `core/validation.ts` changes production behavior. Observatory building orders/completions may retain `highGround: {campusTileId, sourceTileId}`; the installed town retains the same values in `buildingHighGround.observatory`. These records require `observatory-learning`, a completed Campus belonging to that exact town, known integer tile identities and source adjacency to that Campus. The mapping is required iff Observatory is installed, and unknown keys, absent provenance, other-building provenance and mismatched retained aliases refuse.

Active paid work and completed history preserve their original source even if its terrain, elevation or ownership later changes. Validation does not select a replacement, compare historic costs/work/output with current tuning, or require membership in the bounded recent event feed. When the retained completion event exists, its type, round, town-center tile, actor and target must agree with the completion. Existing district ownership/topology guards remain in force for the Campus itself.

Every non-null Observatory operation requires its resident snapshot, because this building originates after resident-capacity. Historical ordinary building receipts retain their existing optional-resident compatibility. The operation schema otherwise reuses existing atomic payment, allocation and status validation; no ordinary resource or strategic stock schema changes.

No SQL migration, repository, HTTP/authentication or public grammar change is needed. Generic state serialization and exact public detail already retain the structured building record. Local public reader evidence does not imply that an unpublished detail endpoint is available on the deployed service.
