## Boundary and observed facts

`GoalDelivery` owns one isolated temporary project. Every lifecycle operation uses
`cargo run --locked --quiet --manifest-path <current-source>/Cargo.toml --bin blabla`.
No installed executable, task-record editing, invented check evidence or copied
closure engine is used. The fixture's Python check really reads its source and
artifact, and its finite two-step counter really receives canonical verification.
Its GREEN receipt belongs only to that temporary project.

Eligibility is operation-specific. It comes from parsed registered goal/system and
model authority, the stored task state/acceptance, actual tracked-readiness and
challenge fingerprints, current claim/review views and actual canonical status.
The two close predicates distinguish current GREEN from prior actual GREEN plus
implementation-only drift. Resolution additionally checks the exact retained claim
digest, closed Partial/Blocked source, assigned current independent review and an
actual terminal artifact. The fixture selector chooses preparations and command
payloads; it does not set eligibility or acceptance. No cloned invocation defines
its own prerequisite. Positive controls independently require qualified fixtures to
be eligible and to succeed; refuse-all cannot satisfy them.

These checks intentionally describe the finite supported preparations. They are
not a second general-purpose workflow resolver. Actual source CLI decisions remain
the result. Exit0 must carry a task object, while a refusal requires exit2 and the
actual task category. Cargo errors, malformed output, memory/configuration errors,
signals and exhausted budgets remain adapter errors.
