## Execution and observation

`bridge/bounded_results.rs` creates a disposable project with a real independent
JSON-line counter, a Rust structure rule, two declared tasks and a focused Python
check. It invokes the current source with `cargo run --locked --quiet
--manifest-path <source>/Cargo.toml --bin blabla -- --project <fixture> --json`.
Open, accept, evidence, challenge, READY and canonical finish all actually execute.
The fixture's `owner` and `worker` names are synthetic process-policy attestations,
not claims that those models performed reasoning. No GREEN record or evidence
receipt is authored by the probe. The counter cannot recurse into the root adapter.

Default/reset is explicitly uninitialized: no bounded CLI project or Cargo child
is created. All eligibility/acceptance observations are false, including
`bounded_fixture_initialized`; reset discards any existing fixture. Named `bounded_success_fixture` and `ordinary_success_fixture` actions prepare
actual qualified states. `bounded_result_fixture` consumes the real positional
argument array; integer kinds normalize with `rem_euclid(9)`:

| Kind | Actual prepared boundary |
| --- | --- |
| 0 | Prior overall canonical GREEN, then another declared task's report changes |
| 1 | Current overall canonical GREEN |
| 2 | Kind 0 plus changed focused task input |
| 3 | Kind 0 plus unconfirmed owner amendment during the worker carry |
| 4 | Latest genuine behavior RED, repaired helper and report drift |
| 5 | Latest genuine structure RED with behavior GREEN, repaired entry and report drift |
| 6 | Kind 0, requested model outside declared owner policy |
| 7 | Kind 0, whitespace-only reason |
| 8 | Kind 0 plus changed verification profile |

Once initialized, every close uses exactly the last prepared project. A first
explicit close is the owner-defined composite action: initialize the genuine
current-GREEN READY fixture, capture its actual decision inputs, then execute that
close. The prior uninitialized observation is not represented as a READY world.
Record-preservation facts compare the actual close interval after preparation.
Ordinary first-close can succeed; bounded first-close really refuses current GREEN.
Exit zero plus persisted CLOSED
state is acceptance; only exit two with structured `category: task` is a decision
refusal. Missing arguments/actions, malformed JSON, launch failures, unexpected
exits and exhausted process budgets are adapter errors. No case kind predicts the
answer. Repeat closes reach the real terminal refusal and preserve the task.

Current status, task-show, tracked readiness/challenge functions and actual grounded
challenge classes supply observations. Challenge is read-only for the READY/CLOSED
states used here. Current task readiness is separate from evidence freshness. Owner
attestation is checked against parsed process policy. Prior GREEN is the observed
canonical finish result paired with the exact status bytes it wrote, including an
actual later RED finish replacing earlier GREEN history.

Basis validation compares every persisted field with the actual request, prior
record and `RelevantRevision`; the fixture's only two memory identities are projected
from its parsed worker role/model policy using the existing fingerprint encoding.
This small fixture-specific observation does not implement acceptance eligibility.
Status and optional verification-marker bytes distinguish absence from read errors.
Before/after status eligibility fields, tree and relevant revision are compared;
ordinary success may remain GREEN, while bounded success leaves the project stale.
Observation returns captured facts without invoking close or refreshing evidence.
Legacy adapter actions and this probe preserve each other's fields.

## Finite local cost and limits

Before the lazy repair, the seven-test measurement in
`/tmp/bounded-bridge-final-measure.log` passed in
15.91 seconds while several fixture paths ran concurrently. Actual runtime source
startup plus initial reset took 3,142 ms. Measured runtime requests were 1,781 ms
for parameterized setup, 1,453/1,248 ms for the named setups, and 1,072/752 ms for
bounded/ordinary close. The same run's internal fixture timings ranged from
760–1,841 ms for parameterized setup and 472–1,243 ms for close; whole adapter batch
times include several requests and must not be compared to a per-request limit.
An earlier redundant initial construction/first-reset path reached 4,925 ms and
was removed without changing either budget. Later cost research showed that even
one eager fixture per legacy reset was too expensive, so the current lazy repair
removes all unused bounded preparation, not merely the duplicate first reset.

The nine-test lazy run (`/tmp/bounded-lazy-green.log`) passes in 13.84 seconds.
Under that concurrent load, first-use setup-plus-close costs 3,856 ms for bounded
refusal and 4,005 ms for ordinary acceptance. These remain inside the existing
budgets but show why a prepared close timing alone is insufficient. A separate
15-request warm sequence is retained at `/tmp/bounded-probe-lazy-cost-run.log`;
its explicit setup/close work remains genuine and its root status hash is unchanged.
The earlier eager measurement and actual failing sentinel are preserved; no
universal speedup or worst-case latency claim is made.

Each probe action has a 4,500 ms internal deadline shared across its subprocesses
and a 2 MiB combined output ceiling per invocation. On this Unix environment,
time/output failure kills the Cargo process group and returns an adapter error.
A cold source rebuild, contention or a different machine can still exceed the
existing request allowance; this finite local run is no latency guarantee or
old-version speedup claim. No automatic timeout increase is proposed. No arbitrary
nested test suite, installed executable or manually trusted target binary is used.

The sequential comparisons cannot prove that the production final reread ran or
survives an interleaving. The separately accepted 16 exact-core checkpoint cases
remain the race evidence; this bridge neither repeats them nor exposes their test
callback. Recursive-review races and malformed historical records remain covered
by the existing focused implementation packet, not this finite fixture set. The
owner must retain that distinction when deciding the temporal rule's promotion.
