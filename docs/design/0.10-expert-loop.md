# BlaBla 0.10 design for review

Status: working release design, 30 September 2026. Baseline: repository commit `7570503`.
This document records the release design for review in the working pull request. It is not an implementation plan or evidence that the proposed features already work.

## Purpose and release outcome

BlaBla should let a very small, fast expert repeatedly help other models stay useful throughout a development workflow, using the project's own memory rather than a growing generic prompt.
The expert notices a bounded problem, points to the relevant goal, rule or expertise, and returns control to the model doing the work.
The project benefit to establish is less owner steering and avoidable rework without reducing correctness, hiding uncertainty or adding a costly stream of interruptions.
“Continuous” means revisiting relevant observed checkpoints during planning, implementation, checking and review; it does not imply access to every host action or private reasoning.

The release has four workstreams with separate acceptance evidence:
1. Repair confirmed 0.9 task and verification gaps so the existing foundation is dependable.
2. Add reusable typed judgments and a compact, revision-aware expert evaluation boundary.
3. Connect one real host, first in shadow mode and then with advisory delivery at supported checkpoints.
4. Establish usefulness through deterministic tests, recorded replay and matched live evaluations.

The recommendation is a narrow advisory subsystem. Keeping only today's `task ask` / `task decide` is simpler but still relies on a caller asking at the right moment; replacing the workflow with an agent orchestrator would exceed the mission and obscure authority.

## Preserve the current foundation

`mission.bla`, `system.bla`, `process.bla`, registered Knowledge, goals, behavior/structure contracts and bounded tasks remain the project model.
Existing `status` and `explain` remain the entry and progressive-disclosure surfaces; there is no competing context entry command.
`finish` remains the sole project completion command. Goals and project memory do not become completion layers, and expert judgments never change `OVERALL`, deterministic rule verdicts or verifier exit codes.
`challenge` remains a deterministic check of recorded facts. The expert can consume its report, but it cannot create authoritative challenge evidence from a model opinion.
Owner intent remains authoritative about purpose. An expert can flag an apparent conflict and name the assumption; it cannot rewrite the owner's goals, contracts, verification profile or permissions.
Existing worker confidence, `--model`, questions, decisions and lens assessments remain attestations. New provider probabilities must not be mixed into those self-reports.
A model name reported by a host is provenance with the host's stated trust level, not proof of identity or proof that the worker followed an intervention.

## Authored judgments and project bindings

Extend the existing Knowledge memory parser with one fixed typed judgment declaration, alongside unchanged packs and rulings; use the same explicit manifest registration by path.
A reusable judgment declares its pack, stable name, purpose, required context slots, literal question/criteria, one output type and allowable intervention template kinds.
The only output types are Choice over named alternatives, Noul for a stated proposition, and Score over explicitly ordered levels. No loops, expressions, user functions, generated code or open-ended response schema are added.
Judgment identities are pack-qualified so independent packs can reuse local names. Exact grammar spelling is a later mechanical interface decision; these fields and semantics are the contract for this design.
Portable Knowledge declares expertise and generic context slots. It never embeds this project's paths, task names, role permissions, goals or contract identities.
Project-local bindings live in Process memory: they select a judgment, eligible roles/checkpoint kinds, and resolve its slots to existing goal, rule, contract, system or knowledge identities.
This preserves the current direction of routing into reusable Knowledge. Bindings grant no additional scope and cannot override a role's existing verification or write authority.
Validation rejects duplicate identities, unresolved bindings, incompatible output criteria, unsupported slot names and templates needing data their binding cannot supply.
A valid definition may still lack facts at runtime; that is an explicit abstention reason rather than invalid authored memory or a fabricated answer.
`status` lists configured expert mode/capability concisely; `explain` expands one judgment or binding and its sources. Projects that register none behave as before.

Initial judgment families are deliberately small:
- Goal drift: compare the current proposal or observed change with the assigned goal and relevant mission priorities; an intentional owner-approved goal change is separate evidence.
- Expertise selection: select from a resolved shortlist of relevant packs/rulings and determine whether any is useful. A forced best choice alone must not force a suggestion.
- Unsupported claim: compare a specific worker claim with supplied evidence. Exact claims about exit codes, freshness or completion are checked in code before semantic judgment.
- Repeated failed approach: compare recent failed attempts, their observed outcomes and stated hypotheses; distinguish a justified repeat or new evidence from an unproductive loop.

A judgment evaluates one concrete question. Related questions may share a compact packet and run together, but the decision policy cannot assume they read one another's answers.

## Observation and context contract

A host adapter supplies an observed event; the project layer adds trusted repository/task facts and resolves only the memory required by eligible judgments.
The expert does not crawl arbitrary files, ingest the whole conversation or ask the provider to discover project identities.
The packet contains:
- Event identity, run/task identity, host identity and capability report, event kind, observed sequence/checkpoint and timestamp
- Task acceptance epoch, relevant task-content digest, write scope and declared input/deliverable digests; project memory and contract fingerprints
- Resolved goal/rule/knowledge identities with the short authoritative text needed for the question
- Bounded observed action/tool-result/claim excerpts, evidence IDs, source type, capture location and observed revision
- Recent relevant attempt and intervention history, plus explicit missing, unknown, truncated and unavailable fields

Host observations, deterministic tool outputs, worker statements and expert inferences are separately typed; quoted worker claims never become observed facts through summarization.
The same relevant facts produce the same canonical packet and hash. Unrelated tree edits do not invalidate a task-local judgment; edits to its evidence, bindings or checked inputs do.
Use a shared revision/dependency calculation for review freshness and expert validity, while preserving existing receipt behavior for notes and unrelated concurrent work.
Missing sequence events, unresolved revisions or truncated necessary evidence prevent an actionable judgment. Missing optional context remains visible in the trace.
Apply bounded selection and truncation before inference, with byte/token accounting and omission markers; each judgment sees only its declared slots.
Treat source text as untrusted data, test adversarial instructions inside it, and never let it select endpoints, templates, executable commands or authority.
Keep credentials out of authored memory, packets and traces. Hosted providers receive only the explicitly selected, redacted packet through a configured provider; local execution remains an option.

## Provider and decision boundary

The core owns typed requests and results; small provider adapters own transport and validate provider-specific responses. A deterministic fake supports ordinary tests without network access.
A result carries the exact question identity, packet hash, provider/model/checkpoint identity, question/template fingerprint, elapsed times, and one typed answer or a typed failure.
For Jev/Kev, retain Choice probabilities, Noul probability, and Score distribution/expectation separately, including the provider's confidence statistic where present.
Confidence describes a distribution; it is not measured accuracy. Score is an ordered judgment, not precise arithmetic. Calibration and thresholds belong to a particular provider, model, question and output type.
A generative model such as Luna may return the same bounded choices for an initial baseline, but unsupported probability fields are absent; a generated certainty claim is marked self-report and never substituted for a model probability.
Validate answer keys, allowed alternatives, numeric ranges, finite values and complete required distributions. Unknown/missing answers, timeout, cancellation, transport errors and malformed output are explicit failures, never “no issue.”
Provider work runs outside behavior/structure verification. Count, compare revisions, calculate durations, enforce scope and decide exact statuses in deterministic code.
Bound request time, context size, concurrency and retry attempts. Retries retain request identity; superseded or cancelled work cannot inject a late result.

The first available baseline is Luna with low reasoning, with reasoning-off only where actually supported. A local Kev-0.8B CPU feasibility check is allowed; local execution speed and suitability must be measured rather than assumed.
The official Kev-0.8B model card warns against tool-call routing; this candidate is a bounded nudge-classification experiment, never the default route controller. A runnable small model still must earn its role on BlaBla-specific cases.
Jev and Kev fit the typed provider boundary, but advertised API compatibility does not establish a working installation or equivalent calibration.
No external server or user API account is a prerequisite for design, fake-provider tests, replay or initial dogfooding.
Each provider claimed as live-supported needs actual Choice/Noul/Score smoke evidence with pinned versions and malformed-response/error handling. Without that run it is labelled unverified, including Jev if no endpoint is available.
Luna's baseline gets its own structured-output smoke record and is never described as a verified Jev/Kev probability provider.

## Deterministic intervention policy

After a valid result, BlaBla chooses one of silence, abstain, advisory nudge or escalation request. These are ordinary outcomes, not success/failure labels for the project.
Silence means the relevant observed evidence justified no intervention. Abstain names missing evidence, unsuitable uncertainty, an unverified provider or a failed evaluation.
An escalation request identifies a decision for the existing orchestrator/owner; it does not automatically change a task state, spawn work or authorize a consequential action.
The policy is deterministic over validated answers, current evidence, capability and recorded settings. The provider does not generate the intervention text or decide what authority it possesses.
Render a compact template with the actual task/goal/rule/ruling IDs, cited evidence IDs, the bounded concern and an existing safe next route such as reading a named identity or reconsidering the current hypothesis.
All references must resolve against the packet; the model may choose only supplied candidate IDs. Unknown or stale references cause abstention before rendering.
Templates cannot execute commands, edit files, widen scope, alter contracts, resolve findings or close tasks. Worker acknowledgment is recorded separately from observed corrective action.

Immediately before delivery, recheck the relevant revision and host checkpoint. An old result is recorded as stale and discarded, not delivered with a warning after the worker has moved on.
Use an idempotency key over task/acceptance, judgment binding, relevant evidence revision and concern/target identity; repeat events and transport retries cannot deliver duplicate nudges.
Suppress the same unresolved concern until material evidence changes, it is resolved, or the host explicitly requests reconsideration. Mere passage of time is not a reason to nag again.
Coalesce eligible concerns at one checkpoint; deterministic safety facts and existing task blockers take precedence, with stable ordering and a bounded delivery budget.
Keep suppression and delivery receipts under `.blabla/`; distinguish proposed, delivered, acknowledged, declined, stale and observed-resolved outcomes.
An acknowledgment cannot count as resolution. A worker declining a nudge does not erase the evidence or silently create permission.

No arbitrary global confidence threshold is part of this design. Before enabling a judgment in advisory mode, freeze its false-nudge tolerance and end-to-end latency budget, select a policy on a labelled development set, and assess it on untouched holdout cases.
If no policy satisfies that declared tradeoff, that judgment stays shadow-only. A provider/model/question change requires a fresh calibration record rather than inheriting a convenient threshold.

## One host integration and rollout

One host adapter is the release target; there is no universal hook system or support claim for every coding host.
The first capability probe targets the installed Codex CLI, using only interfaces confirmed for that installed version. Before selecting the adapter, inspect the host's official interface and prove three things in a harmless local run: observable checkpoints, timely delivery into the same task, and traceable delivery receipts.
The integration decision records the exact host/version, observation gaps, whether the worker pauses, and whether delivery can affect the next step. CLI presence alone proves none of these capabilities.
Prefer the available host with those verified capabilities. If it only supports a wrapper between turns, ship that named checkpoint adapter and say explicitly that it cannot stop an action already in progress.
If no host supports even between-turn delivery, keep replay/shadow evaluation available and report the live advisory milestone blocked; do not claim continuous steering from a report-only tool.
The bounded research deliverable is this capability record and one selected adapter, not a survey or a new host runtime.

Shadow mode records would-be judgments and interventions but sends nothing to the worker. Advisory mode delivers at verified checkpoints after the relevant quality gates pass.
Neither mode adds hard enforcement. Existing deterministic task transitions continue to gate what they already gate; the host may enforce only capabilities actually demonstrated and separately declared.
Disable the expert without affecting ordinary `status`, `challenge`, `task`, `check` or `finish`. Provider outages leave deterministic checks available and the advisory condition visibly unevaluated.

## Confirmed 0.9 carryover

Source inspection at `7570503` is the baseline, not the historical ledger's “Open” labels. Every repair needs a failing regression and a deliberate product break that its test detects.
- Declared-check identity: evidence must bind the exact command or argv and input revision. Replacing argv A with B invalidates A's success, including when the check changes its own task while running; reloading a record alone cannot grant B credit.
- Task withdrawal: add an orchestrator-attested terminal withdrawn outcome with a reason and retained history, distinct from successful close. It releases scope but claims no completed deliverables; unresolved changed paths remain explicitly accounted for rather than disappearing.
- Overlapping scopes: refuse intersecting write scopes at task opening and widening, including directory/file and normalized-path intersections. Read-only inputs may overlap; concurrent writers require a separately authorized scope reassignment, not silent attribution.
- Lens freshness: bind assessment credit to the carrying worker/acceptance epoch and relevant expertise revision; replacement acceptance cannot inherit another worker's lens assessment merely because its pack name matches.
- Review freshness: explicitly link a review task to the reviewed task and its relevant revision/inputs. Rework invalidates approval evidence; unrelated notes/concurrent paths do not. Existing manual `--input` freshness remains useful but does not replace this relation.
- Superseded model proposals: unresolved exception requests remain history but cannot block a replacement worker they no longer concern; a current unapproved exception still blocks.
- Task view clarity: show the declared check as task data in READY and CLOSED as well as active states. Render answered/overruled decisions from their current state, not the original below-floor flag.
- Challenge and recovery wording: distinguish task-assignment clearance from project-level challenges. Correct restore-or-block guidance without pretending that merely blocking repairs an out-of-scope edit; if safe restoration is uncertain, preserve evidence and escalate rather than undo another worker's work.
- Composition behavior: identical-name, identical-type state is intentionally shared today; incompatible types already error. Add an explicit diagnostic identifying cross-contract sharing and test an accidental-collision example before choosing any stricter authoring change; do not blanket-reject valid composition.
- Composition-stable witness steering: uncovered-target selection, replay prefixes, preparatory actions and literal/state guidance already exist. Reproduce the historical starvation against current code, then repair only demonstrated gaps and retain composition regressions. Raising global campaign length alone is not acceptance, and bounded search still permits honest YELLOW.

Already shipped mechanisms such as model aliases, typed questions/decisions, attestation, empty-contract rejection, project timeout inheritance and the direct evaluation driver must be tested, not described as missing features again.
Historical “fixed” or “needs retest” entries remain distinct from new product defects. Update the ledger with reproduction, source/test evidence and remaining limitations instead of claiming all 0.9 observations resolved.

## Components and interfaces

Keep authored validation in `src/memory`, task/revision ownership in `src/project/task`, and host/provider-specific transport at the boundary of a small expert subsystem.
The expert subsystem separates packet selection, typed evaluation, deterministic policy/rendering and trace/replay. Its stable seam accepts a packet plus definitions and returns a typed advisory result; it does not own a task runner.
The project layer composes existing memory/task/challenge views into packets. Neither the skeptic nor the behavior/structure pipelines depends on model transports.
Expose a host-independent JSON Lines evaluation entry that accepts the packet and returns the typed result, plus an offline replay operation; human output renders the same result value. This makes the harness usable before host selection without requiring a persistent server. Add only the host surface needed for the selected adapter.
Runtime records and traces live under `.blabla/`, outside implementation fingerprints. Trace records carry implementation/model/prompt fingerprints, not a new family of versioned public schemas.
Record enough selected input and raw validated output to reproduce each decision, with source hashes, deterministic settings, suppression reasons and delivery receipts; omit secrets and unrelated transcript contents.
Offline replay of a saved response must reproduce policy and template output without network calls. Re-evaluating saved input with a model is a different, explicitly nondeterministic comparison.
Keep trace capture bounded and visible, with explicit retention and deletion controls; a truncated trace must declare which evaluation questions it cannot support.

## Verification and evidence of usefulness

First establish an unchanged-checkout baseline through Cargo and the existing product gate. Cargo/Rust were unavailable during the source inspection behind this draft, so no Rust tests, gate result or current GREEN is claimed here; baseline execution is a separate release record.
Use TDD for repairs and new boundaries: a regression fails first, the minimal change passes, and a deliberate mutation proves the test checks the real production path rather than a copied predicate or fabricated observation.
Deterministic coverage includes unresolved references, unknown facts, unsupported provider capability, invalid responses, cancellation races, event duplication, stale results, worker replacement, out-of-order events and repeated-nudge suppression.
Task tests cover command/argv identity changes and mid-check mutations, withdrawal without false completion, atomic overlap checks, review invalidation, model-specific lens credit, concurrent edits and evidence arriving after a task changes state.
Self-hosting contracts exercise real seams. Falsification establishes dependence on a named fact; it does not replace a real mutation that must produce RED rather than merely unexercised YELLOW.
Run the existing `experiments/gate.py`, rebuilding the bridge from current source, plus the added fake-provider/host tests on both Linux and Windows CI. Live services are outside the credential-free product gate.

Start expert evaluation with labelled event traces containing both intervention-worthy and ordinary no-intervention checkpoints, ambiguous/missing context, legitimate retries, adversarial claims and stale evidence.
Separate development/calibration data from held-out evaluation, and retain per-judgment/provider results and failure reasons. Replay proves decision mechanics, not benefit to a live worker.
Run matched live arms from the same frozen repository/task inputs: current BlaBla with expert off, shadow mode, and advisory mode; hold worker model, tools, host, onboarding, rules, budgets and environment constant.
Predeclare run counts and grading rules, report completed and incomplete runs, and repeat independent tasks/runs rather than generalizing a single success. Recheck the frozen baseline before each arm.
Measure:
- False nudges / all delivered nudges, and missed justified nudges / all labelled justified intervention opportunities, including skipped, silent, abstained and failed evaluations
- Delivery coverage / eligible observed checkpoints, observation gaps, abstentions, provider failures, duplicate/stale rejections and suppression counts
- Accepted or acknowledged nudges separately from observed corrections; correctness and scope violations use independent graders
- Owner interventions and steering/rework time per completed task, with incomplete-task outcomes reported separately
- End-to-end event-to-delivery p50/p95 latency and added worker wall time, separating context retrieval, inference, queueing and delivery; also calls, input size and cost when measurable

Promote each judgment only when its frozen holdout quality/latency policy passes and live matched evidence supports reduced steering without a correctness regression; otherwise leave that judgment disabled or shadow-only and publish the limitation.
Do not present saved tokens, model microbenchmarks, a fake provider or a deterministic replay as proof of useful continuous assistance.

## Compatibility and release boundaries

This repository allows breaking contract, CLI, JSON and exit-code changes in minor releases, listed under Breaking; 0.10 may use that policy. Patch releases remain non-breaking.
Keep one current language and API. Document changes and required revalidation of existing task evidence; do not create a versioned-schema framework, migrations or permanent compatibility branches.
New advisory failure/result fields must not redefine existing completion values or imply that a model certified a deterministic fact. A missing expert configuration changes no current project behavior.
The release report distinguishes core gate results, repaired carryover cases, provider certification, host capabilities, shadow evidence and live advisory results.
Out of scope: automatic contract/profile rewriting, broad orchestration, fine-tuning, a training platform, dashboards, universal host hooks, a general policy DSL, autonomous remediation and claims of formal completeness.
