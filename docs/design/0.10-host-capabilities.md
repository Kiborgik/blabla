## Reproduce safe discovery

```sh
python experiments/probe_expert_host.py --codex codex --out artifacts/expert-host
```

For the bounded repository assignment, the initial output directory was `.blabla/scratch/expert-host-capability/discovery`; the reviewed implementation was rerun into `discovery-round1` below the same task scratch directory. The exact argv, exit code, duration, stdout/stderr receipts and truncation indicators are in its JSON. Commands are executed directly, with no shell. The reviewed capture reads raw bytes in fixed 8 KiB chunks, incrementally counts and hashes them, and retains at most 16 KiB of raw prefix per stream; only that retained prefix is decoded for display. `capture_complete` indicates whether EOF was observed, so an incomplete stream hash cannot be mistaken for the full stream. Commands run in a new POSIX session; their process group is killed at the deadline and on return, and the direct child is reaped. Each command has a 60-second timeout by default, with a bounded cleanup/drain interval. This containment implementation targets the observed Linux/POSIX host. Other platforms return an unavailable record before launch; Windows execution is not certified. Discovery and schema generation use a newly created, private `CODEX_HOME` below the output directory; no existing config or hook file is rewritten. Login status uses the inherited authentication location without reading credentials into Python. Its raw output is omitted from the record.

## Verified runtime blocker

Earlier bounded exec attempts are retained in `/workspace/shared/blabla-host-probe/luna-smoke*.jsonl` and `.stderr`. The original and sqlite/log-override runs stopped with `Read-only file system (os error 30)`. A fresh writable `CODEX_HOME` reached `thread/start`, then failed while loading AGENTS instructions: `app-server socket directory must be a user-owned directory with mode 0700`. A fresh 0700 `XDG_RUNTIME_DIR` produced the same error. These runs produced no successful inference, observed checkpoint, marker delivery or receipt. Their logs do not retain complete invocation argv, so they are not advertised as fully reproducible smoke protocols.

Metadata-only inspection found `/tmp/codex-daemon-1000` owned by effective uid 1000 with mode `0000`. The installed binary contains the `codex-daemon-` marker. The current [official daemon-directory implementation](https://github.com/openai/codex/blob/main/codex-rs/uds/src/daemon_directory.rs) reserves `/tmp/codex-daemon-<uid>`, validates exact owner and 0700 mode, and makes the location independent of HOME, TMPDIR, CODEX_HOME and command settings. Together these observations explain the failed runtime-directory experiment; the current upstream source is diagnostic corroboration, not a claim that this binary was built from upstream HEAD. The installed version's pinned source tag was not retrieved.

The reserved directory was left unchanged. No chmod, ownership change, credential copy, sandbox relaxation or hook-trust bypass was attempted. No further live Codex runs were made after this diagnosis. Supported per-invocation XDG/CODEX_HOME relocation cannot repair this fixed-directory validation failure. Restoring host runtime availability requires an authorized environment-owner repair or a working executor, outside this bounded task.

Project-local hooks require project trust, and non-managed hook definitions require trust review. This task did not alter persisted trust or bypass it. The installed generated protocol contains `turn/steer`: `TurnSteerParams` requires `threadId`, `expectedTurnId` and `input`, and `TurnSteerResponse` requires `turnId`. `turn/start` requires `threadId` and `input`. The [official app-server documentation](https://learn.chatgpt.com/docs/app-server) describes that JSONL protocol. Schema discovery does not demonstrate successful input insertion or model-visible receipt.

It must bind the receipt to the event/checkpoint and show the marker affecting the next step. That sequence was not executed and no adapter was selected. A between-turn wrapper, even when later verified, has observation gaps within turns and cannot stop an action already in progress. Offline/fake-host checks remain useful without granting live capability credit.

## Verification and release boundary

Deliberate production mutations granting delivery, granting supported provider status, and rewriting the fixture config each made the relevant regression fail; all mutations were restored and that focused check passed. Independent review then found that the original `capture_output` implementation buffered complete output, killed only the direct child on timeout, and normalized command-output bytes before hashing. Three new actual subprocess regressions failed before the fix: a surviving descendant wrote a late marker, 4 MiB outputs exceeded the retained limit, and CRLF/invalid-UTF-8 bytes had the wrong hash. The reviewed implementation passes all 12 focused tests, including both 4 MiB output streams with less than 2 MiB traced peak Python allocation, raw-byte hash preservation, and process-group termination before the descendant can act. The initial discovery receipt used normalized-text command hashes; `discovery-round1/capabilities.json` uses raw incremental receipts. Baseline and generated-file hashes were already raw and are unchanged.

No product behavior, contract, verification profile or global host configuration changed. Core baseline evidence is recorded separately in [release evidence](0.10-release-evidence.md). Host/provider blockers do not turn that unchanged core baseline into a regression, and baseline GREEN cannot certify this release worktree.
