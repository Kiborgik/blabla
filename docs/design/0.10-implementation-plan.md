# BlaBla 0.10 Expert Loop Implementation Plan

> Implement one reviewable task at a time. Each task includes a failing regression, the smallest production change, verification and a logical commit owned by the orchestrator. Implementation workers do not mutate Git state. This is a plan, not a claim that the release gates have passed.

**Goal:** Repair the demonstrated 0.9 gaps and add a revision-aware advisory expert that earns delivery at one verified host's checkpoints.

**Architecture:** Preserve the existing memory, bounded-task and deterministic-verifier boundaries. Knowledge declares fixed typed questions; Process binds them to the project. A small expert subsystem selects bounded context, validates provider results, applies deterministic policy and records replayable decisions; a thin host adapter owns observation and delivery.

**Tech stack:** Rust edition 2024, Rust 1.90 minimum, existing serde/serde_json/clap dependencies; Python 3.10+ standard-library host/evaluation helpers. No server or new schema framework is required.

**Spec:** [0.10 expert-loop design](0.10-expert-loop.md). Source baseline: `7570503`; initial design commit: `3328307`.

## Global constraints

- `finish` remains the sole project completion command. Expert opinions never change `OVERALL`, deterministic verdicts or verifier exit codes
- `challenge` checks recorded facts. Worker confidence and `--model` remain attestations, distinct from provider distributions and verified host provenance
- Knowledge stays reusable; project paths, identities, roles and checkpoint bindings belong in Process and task records
- Only Choice, Noul and ordered Score outputs are supported. No executable templates, policy DSL, arbitrary response schemas or autonomous remediation
- An absent expert configuration preserves current project behavior. Provider failure must leave deterministic checks available
- One proven host adapter is the live target. CLI installation, API documentation and synthetic model calls are not proof of usable host observation, authentication or delivery
- Run repository commands through `cargo run --quiet --bin blabla --`; rebuild the bridge before `finish`. Never substitute an installed binary
- Breaking CLI/JSON/record changes are allowed in 0.10 and must be listed under Breaking. Retain one current language/API; old unbound evidence is history, not current credit
- Tests assert IDs, structured fields and exit codes, not English copy. Deliberate production mutations must make the relevant regression fail
- Keep credentials, unrestricted transcripts and unselected files out of packets, traces and committed evidence. Do not change global host configuration or extract credentials
- Production implementation code contains no comments or docstrings; communicate through names, small functions and tests
- Workers use explicitly assigned disjoint write scopes and never commit, push, branch or otherwise mutate Git; the orchestrator owns logical commits, integration and the broad gate. Every commit checkbox below is an orchestrator action
- Contract, manifest and memory edits require an explicit authoring assignment. Do not weaken a contract or verification profile to obtain GREEN
- Read current role model allowlists through the source CLI before recording acceptance; use the actual permitted model as an attestation, never spoof one. The current orchestrator role permits `gpt-6-astra`
- No attribution trailers, universal-host claims, default Kev route control, speed claims from a microbenchmark, or usefulness claims from replay alone

## Review focus

1. A check changes its argv, acceptance or inputs while it is running: retain its actual observation without giving the replacement declaration credit (Task 2)
2. Two writers race, or withdrawal leaves changed files: reject overlapping ownership atomically and keep unresolved changes visible after scope release (Task 3)
3. A replacement worker or reworked reviewed task inherits stale credit: require the current acceptance and dependency revision, while ignoring unrelated notes/paths (Task 4)
4. Quoted instructions, incomplete context or a forged provider reference looks persuasive: treat it as data and abstain before rendering or delivery (Tasks 6–9)
5. A provider finishes after cancellation, a host advances, or a delivery receipt is lost: never deliver stale/duplicate advice, and never treat acknowledgment as resolution (Tasks 8–10)

## Fixed authored surface

Use the current parser's flat quoted fields/lists. Do not extend the generic memory grammar.

```bla
knowledge "expert-review" {
    purpose "Notice a bounded concern and point back to relevant project memory."
}
ruling "evidence-before-claim" {
    pack "expert-review"
    statement "A claim is supported only by evidence that establishes it."
}
judgment "claim-support" {
    pack "expert-review"
    purpose "Check whether the supplied evidence supports a specific claim."
    requires ["claim", "evidence"]
    question "Does the supplied evidence support the stated claim?"
    criteria "Unknown, missing or unrelated evidence does not establish the claim."
    output "noul"
    proposition "The evidence supports the claim."
    templates ["cite-evidence", "ask-owner"]
}
```

`judgment::<pack>::<name>` is canonical. Required fields are `pack`, `purpose`, `requires`, `question`, `criteria`, `output`, `templates`. Optional fields are `alternatives`, `proposition`, `levels`, `optional`; exactly the output-specific field is required: Choice has at least two distinct identity-safe `alternatives`; Noul has one nonempty `proposition`; Score has at least two distinct identity-safe `levels` in ascending order. Reject other output-specific fields, duplicates and empty criteria. Ordered Score uses zero-based ordinal positions, not user-supplied numerical weights.

The complete slot vocabulary is `task`, `goal`, `mission`, `proposal`, `claim`, `evidence`, `attempts`, `candidates`, `rules`, `system`. `requires` and `optional` are disjoint. The complete template vocabulary is `read-identity`, `cite-evidence`, `reconsider-approach`, `ask-owner`. Text and IDs are never executed.

```bla
binding "claim-check" {
    judgment "judgment::expert-review::claim-support"
    roles ["worker", "reviewer"]
    checkpoints ["tool-result", "claim", "turn-end"]
    rules ["ruling::expert-review::evidence-before-claim"]
}
```

`binding::<name>` is canonical. Required fields are `judgment`, `roles`, `checkpoints`; optional identity lists are `goal`, `mission`, `candidates`, `rules`, `system`. These lists bind same-named slots to existing canonical identities. `task` is the selected task; `proposal`, `claim`, `evidence` and `attempts` come only from typed observations/history. The task's declared goal supplies `goal` when the binding omits it; absence at runtime is explicit. No arbitrary file paths or `slot=value` mini-language. Checkpoints are exactly `plan`, `tool-call`, `tool-result`, `claim`, `turn-end`, `review`; an adapter advertises only those it actually observes. Validate role/identity kinds and reject a template if neither required/optional slots nor binding context can supply its references.

Initial shipped judgments in `knowledge/expert.bla` are `goal-drift` (Choice: `aligned`, `drift`, `unclear`), `expertise-useful` (Noul), `expertise-selection` (Choice over bounded labels `candidate-1` through `candidate-4` and `none`), `claim-support` (Noul), and `failed-approach` (Score: `justified`, `unclear`, `repeating`). The two expertise questions evaluate independently on the same candidate list; selection alone never causes advice. Schedule the expertise pair together or skip it with a visible budget reason, never count a lone selection as sufficient. Candidate labels map deterministically to at most four resolved pack/ruling IDs in the packet. Add an executable fixture for each family; keep repository bindings shadow-only until promoted by Task 11.

## Shared runtime contracts

All new runtime structures derive serde serialization/deserialization; enums use snake_case tags. Unknown fields and unknown enum values at external boundaries are rejected. The following names and ownership are fixed; small private helpers need not be public.

- `task::CheckIdentity`: `Text { command: String } | Argv { argv: Vec<String> }`; never flatten argv into a space-joined identity
- `task::revision::RelevantRevision { acceptance_epoch: u64, task_digest: String, paths: BTreeMap<String, Option<String>>, identities: BTreeMap<String, String> }`; `fingerprint() -> String`
- `knowledge::Judgment { name, pack, purpose, question, criteria: String, requires, optional: Vec<ContextSlot>, output: JudgmentOutput, templates: Vec<TemplateKind> }`; `JudgmentOutput = Choice { alternatives: Vec<String> } | Noul { proposition: String } | Score { levels: Vec<String> }`
- `process::JudgmentBinding { name: String, judgment: String, roles: Vec<String>, checkpoints: Vec<CheckpointKind>, context: BTreeMap<ContextSlot, Vec<String>> }`
- `expert::ExpertMode = Off | Shadow | Advisory`; `ContextSlot`, `TemplateKind`, `CheckpointKind` enumerate exactly the authored values above
- `expert::SourceKind = HostObservation | DeterministicOutput | WorkerStatement | ExpertInference`; retain the kind through selection, truncation and replay
- `expert::Observation { id: String, slot: ContextSlot, kind: SourceKind, capture: String, observed_revision: String, text: String, fact: Option<ObservedFact> }`; `ObservedFact = CommandExit { argv: Vec<String>, exit: i32 } | TaskState { task: String, state: String } | Revision { fingerprint: String }`. Only trusted collection paths may construct authoritative facts
- `expert::HostCapabilities { host: String, version: String, adapter: String, checkpoints: Vec<CheckpointKind>, pauses_worker: bool, same_task_delivery: bool, delivery_receipts: bool, pre_tool_control: bool, gaps: Vec<String> }`
- `expert::ObservedEvent { event_id, run_id, task, checkpoint_id: String, sequence: u64, previous_sequence: Option<u64>, unix_ms: u64, kind: CheckpointKind, host: HostCapabilities, observations: Vec<Observation> }`
- `expert::packet::ContextValue = Present { observations: Vec<Observation> } | Missing | Unknown | Unavailable { reason: String } | Truncated { observations: Vec<Observation>, omitted_bytes: usize }`; required slots containing the last four states cannot produce actionable advice
- `expert::EventStamp` has the `ObservedEvent` metadata fields but no observations. `expert::packet::ExpertPacket { event: EventStamp, binding_id: String, revision: RelevantRevision, context: BTreeMap<ContextSlot, ContextValue>, references: BTreeMap<String, String>, history: Vec<InterventionSummary>, accounting: PacketAccounting, hash: String }`. `references` contains only resolved identities/evidence IDs with bounded authoritative text; history is a bounded projection, not the whole trace. The full observed event never travels inside a per-judgment packet
- `expert::provider::EvaluationRequest { request_id: String, packet: ExpertPacket, judgment: Judgment, question_fingerprint: String, template_fingerprint: String }`; `EvaluationResponse { request_id, packet_hash, question_fingerprint, template_fingerprint: String, provider: ProviderIdentity, timing: EvaluationTiming, usage: ProviderUsage, provider_request_id: Option<String>, outcome: Result<TypedAnswer, ProviderFailure> }`
- `EvaluationBatchRequest { batch_id: String, requests: Vec<EvaluationRequest> }`; `EvaluationBatchResponse { batch_id: String, responses: Vec<EvaluationResponse> }`. A batch has 1–4 independent questions with byte-identical selected context, revision, event stamp and references; only judgment/binding/question identity may differ. Return one response per request ID, including per-question failures, and never let a question read another answer
- `PacketAccounting { selected_bytes: usize, omitted_bytes: usize, estimated_tokens: usize, provider_tokens: Option<usize> }`; `EvaluationTiming { queue_ms: u64, inference_ms: u64, total_ms: u64 }`; `InterventionSummary { request_id, concern, target: String, state: DeliveryState, evidence_revision: String }`
- `ProviderUsage { input_tokens: Option<usize>, output_tokens: Option<usize>, reported_latency_ms: Option<f64> }`; `OutputKind = Choice | Noul | Score`; `ProviderIdentity { provider, model, checkpoint: String, supported_outputs: Vec<OutputKind>, probabilities: bool, certification: Option<String> }`; `TypedAnswer = Choice { pick: String, probabilities: Option<BTreeMap<String,f64>>, confidence: Option<f64> } | Noul { value: Option<bool>, probability: Option<f64>, confidence: Option<f64> } | Score { level: Option<String>, distribution: Option<Vec<f64>>, expectation: Option<f64>, confidence: Option<f64> }`. Generated confidence is an optional separate `self_report: Option<String>` on the response, never a probability field
- `ProviderFailure = Unsupported | Unverified | Timeout | Cancelled | Transport | Malformed | IdentityMismatch`; include bounded diagnostic text beside the enum, not in its discriminant
- `expert::policy::ExpertResult { request_id, packet_hash: String, outcome: AdvisoryOutcome, references: Vec<String>, template: Option<TemplateKind>, message: Option<String>, reason: String }`; `AdvisoryOutcome = Silence | Abstain | Nudge | Escalation`. The reason is a stable machine code

Hashes use deterministic serialization with ordered maps and the existing `project::Fnv` for freshness, not security or authenticity. Include domain tags and complete serialized values; do not concatenate ambiguous command strings. Request/event identity and timings are trace metadata: exclude random IDs, timestamps and timings from the canonical content hash when they do not change the question. Keep run/task/acceptance/checkpoint identity, selected evidence, sequence, source revisions and definitions in the identity checks. Never treat a hash as proof that a caller's claimed observation is true.

`ExpertLimits` defaults: `packet_bytes = 16384`, `excerpt_bytes = 2048`, `history_entries = 8`, `judgments_per_checkpoint = 4`, `request_timeout_ms = 10000`, `concurrency = 1`, `retries = 0`, `deliveries_per_checkpoint = 1`. These are resource limits, not quality thresholds; expose them in recorded settings. Count exact UTF-8 bytes. Record provider-reported token count when available; otherwise label a `ceil(bytes/4)` estimate as estimated. No global probability cutoff.
