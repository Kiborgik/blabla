### Cooperative rendezvous and trust contract

Native `followup_task` can queue into a running child; it has no expected-turn compare-and-send operation. The adapter must not claim that an idle lookup makes its subsequent send atomic.

One enrolled coordinator owns continuation for a run. It records the child identity from the actual spawn/tool result, not from child text. The worker ends its visible turn at an explicit boundary while its BlaBla task remains ACCEPTED. The binding records that completed boundary and an idle observation, then prepares a request-only wake containing the run/checkpoint nonce. **The wake contains no advice.**

At its next boundary the same worker invokes `consume`. Under the adapter's run lock, consume rechecks enrollment, continuation generation, task/epoch, selected revision, permit and reservation immediately before exposing any fixed template. A stale, unobserved or already-consumed request returns no advice. A child-supplied identity is an attestation; the coordinator separately correlates the actual native response origin. These checks provide a cooperative protocol, not authenticated platform identity or interception of arbitrary host messages.

Rendezvous states are `enrolled → boundary_observed → request_reserved → wake_requested → consumed → response_observed`; uncertainty branches to `unknown`, and invalidation to `invalidated`. Wake transport acceptance is never delivery. Consume records exact output exposure; a matching response-origin/request acknowledgment records acknowledgment, and current deterministic evidence records any correction separately. An unknown consume/receipt outcome remains unknown and suppresses redelivery across restart.

Out-of-band continuation is unsupported and invalidates the enrolled generation once observed. An unobserved continuation cannot earn completeness credit. The binding must state this limitation instead of setting general same-task or gap-free capability flags from a successful nonce echo. A real integration review must establish which narrower capabilities the core can truthfully accept; otherwise the run stays ineligible.

The Python live runner communicates with the shipped host skill through a versioned request/result rendezvous. The runner persists a pending host operation; the skill executes the actual native tool and submits its bounded result metadata; the runner validates and advances. Pending is not completed. The schema gate specifies each operation, transition, deadline, evidence origin and restart rule. No Python API for native tools is invented.
