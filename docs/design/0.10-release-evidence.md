# 0.10 release evidence

**Release candidate, not yet published.** The implementation is in [PR #3](https://github.com/Kiborgik/blabla/pull/3); merge, tag and release remain owner decisions. See [what changed](../../CHANGELOG.md#0100-unreleased) and the [working workflow](../agent-workflow.md).

## Release recommendation

**HOLD the product-readiness claim pending a goal-to-outcome demonstration.** BlaBla exists to make useful development progress visible through cheap, actionable feedback, across behavior, content and quality goals. The implementation and packaging receipts below establish important foundations. They do not yet establish that the complete feedback loop reliably keeps work aimed at those goals with acceptable steering cost.

Use the bounded [product feedback plan](0.10-product-goal-feedback.md) to review existing evidence and close that gap. The owner additionally authorized one focused repair to misleading goal-completion guidance. This does not authorize broader product changes, a new paid model experiment or a larger gate. Optional expert benefit remains a separate unqualified claim.

## What real project use established

The [RTS/adventure dogfooding report](../evidence/rts-dogfooding.md) records concrete misses, correction rounds and how they changed BlaBla:

- Explicit requirements and independent reviews caught omitted player behavior, stale evidence and integration defects
- The adventure pipeline exposed ignored task inputs receiving successful-check credit; unobservable inputs are now rejected and old invalid declarations cannot retain current credit
- String-boundary work exposed adapter/persistence defects and a coverage limitation; the [follow-on report](../evidence/rts-string-boundaries.md) preserves the negative result too

These are full-workflow operational findings. Reviewer observations are not relabeled as automatic semantic detection or model nudges. The reports explain the development effect rather than using test totals as the outcome.

A newer private creature-game expansion illustrates the intended product signal: exact playable journeys, distinct identity-to-art bindings, an actual rendered contact sheet and meaningful route witnesses. The owner corrected a test-count proxy and asked for player-visible results. Focused checks then exposed real path and integration misses. The [anonymized case](0.10-product-goal-feedback.md#worked-example-from-a-creature-game) records what was observed, what BlaBla enforced and what still needs acceptance. Its private source and assets are not a public reproducibility package, and the observations are not a controlled estimate of BlaBla's benefit.

A direct self-hosting check at `db29cf7` exposed a product-signal problem: `status` suggested marking `goal::expert-loop-demonstrated-in-real-work` done when its five contract expectations held, although its prose requires unestablished live delivery and matched work. The focused correction routes held expectations to outcome review and states that contract results do not establish broader acceptance. The goal stays active; recorded states, JSON structure, verdicts and `OVERALL` semantics are preserved. This changes the misleading guidance without creating persisted outcome signoff or inferring truth from prose. The [plan](0.10-product-goal-feedback.md#the-goal-signal-gap-and-focused-correction) retains the counterexample and the broader acceptance gap.

## Expert layer: experimental and unqualified

The transport, typed questions, selected packets, deterministic policy, replay and calibration machinery are implemented. Repository bindings remain shadow-only; no judgment is promoted.

Real Kev calibration completed but selected **no feasible policy**: it abstained on the development cases and missed justified nudges. A smaller rendering diagnostic reduced latency but did not establish useful drift detection. The holdout was not reopened to tune the failed policy. See [expert setup and qualification](../expert.md).

Actual installed-host observation/delivery and Luna/Jev provider use remain unverified where the host report says so. Native cooperative between-turn support is not proof of always-on intervention. Deterministic GREEN never changes those capability limits.

## Release preparation

The versioned release body is prepared at `.github/release-notes/notes-v0.10.0.md`, the path required by the tag-triggered release workflow. Cargo, lockfile, plugin and citation versions agree on 0.10.0. `CITATION.cff` omits `date-released` while the candidate is unpublished; the actual publication date belongs there only when the release occurs.

Local preparation checks cover an offline verified Cargo package, a fresh-root install from that unpacked package, and the Linux x86_64 binary archive layout used by the release workflow. Installed and extracted binaries exercise version/help, Todo verification/status and new-project bootstrap outside the source checkout. Dependencies and build caches may be reused; these are clean installation roots, not cold dependency builds.

Preparation exposed two integration constraints: `task check` replaces its input list, so the final declaration repeats every intended source/package input; shared Cargo targets caused contention, so the source CLI and nested packaging/install checks use separate target directories. These are documented command semantics and toolchain behavior, not demonstrated BlaBla defects.

The Windows release zip and its clean-install smoke have not been run here. Windows product CI is distinct from release-artifact verification. No tag, release/crate publication, deployment or publishing workflow is part of these preparation checks.

## Acceptance still required

- Review one bounded goal-to-outcome account covering behavior, content and visual quality: original goal, chosen observation, actual miss/correction, current outcome and remaining acceptance. Reuse existing work; attribute human direction, checks and BlaBla safeguards separately
- Show that a green proxy cannot stand in for an unmet product goal in the release account. Verify the focused self-hosting guidance correction, while keeping unestablished broader outcomes visibly open
- Account for the task ceremony used and the feedback it bought. Use focused checks per slice and one integration gate; no test or command total counts as the product outcome
- Obtain owner release acceptance and final-revision engineering checks; do not infer either from a draft PR or earlier CI

The [acceptance plan](0.10-product-goal-feedback.md#acceptance-for-a-future-010-release) defines the finite review and stopping conditions. A claim of faster development needs a declared matched comparison; no such experiment is required or authorized by this documentation revision. Advisory delivery needs a separately qualified useful expert configuration. The existing evidence supports deterministic contracts, task handoffs and experimental tooling; it does **not** establish faster development, better model judgment or live advisory benefit.

Older source-specific receipts, environment details and correction history are preserved in [historical integration evidence](0.10-release-evidence-history.md). They are audit material, not current setup instructions.
