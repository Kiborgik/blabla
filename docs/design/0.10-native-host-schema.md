# Native host rendezvous and experimental authority

Status: implemented experimental wire contract, independently reviewed, 1 October 2026.
[The completion plan](0.10-host-loop-completion.md) tracks current source verification and
remaining live acceptance. This schema is not a capability certificate, experiment permit,
or evidence of provider quality or improved work. Real calibration, core enrollment and a
graded matched run remain separate requirements.

The selected surface is the model-side native `collaboration` tool surface, with one enrolled
coordinator and cooperating workers at completed, idle between-turn boundaries. Python cannot
invoke those tools. The host skill invokes them; Python validates/normalizes their bounded
results and drives the existing source CLI. Neither component reads private session stores.

## 1. Historical baseline and implemented seams

The controlling source is `src/expert/{mod,packet,provider,policy,trace}.rs`,
`src/project/expert.rs`, `src/project/task/revision.rs`, `src/cli/expert.rs`, and
`experiments/expert_eval.py`.

The following baseline describes the foundation before this native extension. Legacy fixture
calibration and legacy `live()` retain their old semantics; the separate `calibrate-live` and
`live --native-plan` routes now collect real responses and drive resumable native operations.
Available routes do not establish that a real-provider or graded live run has completed.

- `checkpoint()` currently validates events, advances the checkpoint, builds packets and calls
  the provider. It sets a result's advisory mode only if `promotion_matches()` passes; it does
  not currently require promotion before making shadow inference calls
- `TraceStore::reserve()` independently requires advisory runtime/record mode, exact runtime
  identity, replay validity, rebuilt revision, current checkpoint, promotion, deduplication and
  unresolved-budget checks. It commits an `Unknown` suppression entry before returning text
- `promotion_matches()` requires general `pauses_worker`, `same_task_delivery`,
  `delivery_receipts` and empty `gaps`. A successful native nonce echo cannot justify setting
  those general capabilities to true
- `receipt()` recognizes host observations at the current checkpoint, and independently checks
  current task evidence for `ObservedResolved`. An acknowledgment is not that evidence
- `calibrate()` consumes saved authored answers. `live()` does not execute an adapter. Neither
  is real-provider calibration or live execution today

Keep `HostCapabilities` and `ObservedEvent` unchanged. Add the narrow capability and execution
identity below to the experimental run/trace boundary, not to the provider's question schema.
Keep the native host's three general delivery booleans false. Ordinary promotion remains
unchanged and cannot admit this cooperative binding. The bounded implementation comprises:

1. A `pilot` module for attested issue/revoke, scoped admission, clock and budget accounting
2. Experimental/native records in the existing expert ledger under its existing lock, plus
   atomic native operations exposed by the expert CLI
3. A required tagged execution identity on trace/receipt projections; experimental payloads
   have their own directory and cannot be fetched through ordinary delivery
4. Factored common reserve/freshness checks, called by both ordinary reserve and experimental
   reserve/consume; one policy/rendering implementation
5. A worker-side post-work capture and per-binding stamping route, plus saved-response core
   policy fitting for actual-provider calibration and the resumable live runner

No generic host driver, server, new credentials, task runner or platform interception is added.
The orchestrator still creates bounded tasks and children using its normal workflow. The live
runner starts only with already enrolled, accepted, initially idle children.

## 2. Closed notation and scalar rules

The type declarations below are normative wire schemas. `{ field: Type }` is an exact JSON
object; every displayed field is required, including nullable fields. `A | B` is a disjoint
union. Every object union has the displayed literal `kind`; scalar enums and nullable types are the stated exceptions. Unknown/duplicate fields, unknown tags,
missing fields, Boolean-as-integer, non-finite numbers, non-UTF-8, trailing JSON and Markdown
wrappers are rejected. Array bounds are inclusive. No arbitrary `metadata` object exists.

- `Id`: `policy::safe_identifier`, at most 256 UTF-8 bytes; task/binding IDs also require their
  canonical `task::`/`binding::` prefixes and resolution against current project memory
- `Child = { agent_id: Opaque | null, task_name: Opaque }`; `Opaque` is nonempty redacted
  UTF-8, at most 256 bytes. `task_name` is the observed canonical name from the actual spawn
  result. `agent_id` is copied only if that result exposes a separate ID; otherwise it is
  explicitly null. Never fabricate an ID by copying task_name, status agent_name or worker
  text. Slash-containing native task paths are not coerced through `safe_identifier`
- `Digest`: the exact existing core fingerprint string; freshness, never authentication
- `Sha256`: exactly 64 lowercase hexadecimal characters, over bytes unless stated otherwise
- `Nonce`: 32 lowercase hexadecimal characters from the operating system random source,
  generated by the core, never selected by a worker or inference output
- `ProbeNonce`: the same 32-hex format, generated by the shipped deterministic helper for
  preflight challenges and evidence capture-session IDs; it never substitutes for a
  core-generated rendezvous/consume Nonce
- `U64`: JSON integer in `[0, 2^64-1]`; `Positive`: `U64` greater than zero
- `Text`: redacted UTF-8 up to 2,048 bytes; `Brief`: up to 8,192 bytes, frozen before execution
- `Path`: normalized project-relative file path, no absolute path, traversal or symlink;
  `EvidenceRef = { id: Id, path: Path, sha256: Sha256 }`
- `Clock = { boot_id: Opaque, boottime_ms: U64, unix_ms: U64 }`, sampled by trusted core code,
  never accepted as the caller's claim of the current time

Use existing Rust types verbatim for `RelevantRevision`, `HostCapabilities`, `Observation`,
`ProviderIdentity`, `ExpertLimits`, `PolicySettings`, `EvaluationRequest`,
`EvaluationResponse`, `ExpertResult`, `InterventionSummary` and `DeliveryState`; their current strict validators
remain authoritative. Rust computes `RelevantRevision` and its fingerprint. Python never
reimplements FNV, packet hashing, policy selection or revision selection. Experiment manifests
use the evaluator's sorted-key compact UTF-8 JSON SHA-256. Hash comparisons never certify an
observation's origin.

Each native input/output object is at most 65,536 bytes; a trace at most 262,144 bytes. There
are at most 32 observations per boundary, 4 selected judgments, 64 native operations per run,
64 receipts per request and 16 enrolled tasks per run. Existing smaller packet/excerpt limits
still apply. An overflow stops that operation before inference/exposure; no counter wraps or
silent truncation earns eligibility. These are fixed resource ceilings, not quality thresholds.

## 3. Capability, enrollment and checkpoint identity

```text
NativeCapability = {
  kind: "cooperative_between_turn",
  host: HostCapabilities,
  tool_surface: EvidenceRef,
  nonce_round_trip: EvidenceRef,
  boundary: "completed_idle_turn",
  continuation_owner: "single_enrolled_coordinator",
  delivery: "worker_first_action_consume",
  origin: "coordinator_correlated_native_result",
  limitations: ["no_atomic_host_send", "in_turn_unobserved",
                "child_identity_attested", "unobserved_out_of_band_continuation"]
}
Enrollment = {
  run_id: Id, task: Id, acceptance_epoch: Positive,
  child: Child, coordinator: Child, generation: Positive,
  assignment_revision: RelevantRevision,
  spawn_evidence: EvidenceRef, initial_idle_evidence: EvidenceRef,
  capability: NativeCapability
}
BoundaryKey = {
  run_id: Id, task: Id, acceptance_epoch: Positive,
  child: Child, generation: Positive,
  checkpoint_id: Id, sequence: U64, previous_sequence: U64 | null,
  boundary_nonce: Nonce, assignment_revision: RelevantRevision
}
SelectedBinding = {
  binding_id: Id, revision: RelevantRevision, packet_hash: Digest,
  question_fingerprint: Digest, template_fingerprint: Digest
}
Checkpoint = { key: BoundaryKey, selected: SelectedBinding[0..4] }
```

`host.host` is `openai-native-collaboration`, `host.adapter` is `blabla-native-cooperative`.
`host.version` is `unversioned-` followed by the first 16 hex digits of the captured tool-surface
SHA-256. This names the observed tool contract; it does not invent a platform release number.
`checkpoints` is exactly `["turn_end"]`; `pauses_worker`, `same_task_delivery`,
`delivery_receipts`, and `pre_tool_control` are all false. `gaps` contains missing observations
inside the enrolled surface, not the four fixed limitations. Empty `gaps` means only that no
missing enrolled boundary has been detected. It is never called general gap-free observation.

The nonce proof records the actual tool returns, an initially completed/idle child, the request
nonce, and the coordinator-observed origin of the nonce response. It certifies neither
atomic compare-and-send nor intervention correctness. An incomplete proof cannot enroll.
The native skill must be disabled if the current exposed tool surface differs from that proof.

### Closed enrollment evidence and actual-tool projections

Every referenced evidence file is strict bounded JSON, at most 65,536 bytes, with no unknown
fields. EvidenceRef.sha256 is the SHA-256 of its exact UTF-8 file bytes; EvidenceRef.id must equal
its record_id. Paths use the existing project-relative non-symlink rules. These are selected
coordinator-attested projections of actual exposed tool metadata, actual tool results and native
completion notifications, not authenticated platform receipts. Local IDs, sessions and sequence
numbers identify collection records only; they are never called platform request or turn IDs.

```text
NativeToolObservation = {
  kind: "native_tool_observation", schema_version: 1, record_id: Id,
  coordinator: Child, capture_session: ProbeNonce, local_sequence: Positive,
  operation_id: Id | null,
  attestation: "coordinator_observed_native_surface",
  projection: NativeProjection
}
NativeProjection =
  { kind: "tool_surface", source: "exposed_tool_contract", surface: NativeToolSurface }
| { kind: "spawn", tool: "collaboration.spawn_agent",
    requested_task_name: Opaque, returned: Child }
| { kind: "status", tool: "collaboration.list_agents",
    path_prefix: Opaque | null, selected: SelectedStatus | null }
| { kind: "followup", tool: "collaboration.followup_task", target_task_name: Opaque,
    sent: SentProtocol, outcome: "returned_without_error" | "explicit_rejection" | "unknown" }
| { kind: "completion", source: "native_completion_notification",
    origin: Child, marker: NativeMarker }
| { kind: "not_invoked", tool: "collaboration.list_agents" | "collaboration.followup_task"
                              | "collaboration.wait_agent",
    reason: "cancelled_before_call" | "deadline_before_call" }
| { kind: "unavailable", source: "collaboration.spawn_agent" | "collaboration.list_agents"
      | "collaboration.followup_task" | "collaboration.wait_agent"
      | "native_completion_notification" | "exposed_tool_contract",
    reason: "missing_result" | "unrecognized_shape" | "ambiguous_origin" | "tool_error" }
SelectedStatus =
  { kind: "completed", agent_name: Opaque, agent_id: Opaque | null, marker: NativeMarker }
| { kind: "running", agent_name: Opaque, agent_id: Opaque | null }
| { kind: "unknown", agent_name: Opaque, agent_id: Opaque | null }
NativeMarker = InitialReadyMarker | ProbeReadyMarker | ProbeResponse
             | WorkerBoundary | AdviceResponse | NoAdviceResponse
InitialReadyMarker = {
  kind: "blabla_native_ready", schema_version: 1,
  run_id: Id, task: Id, acceptance_epoch: Positive
}
ProbeReadyMarker = { kind: "blabla_native_probe_ready", schema_version: 1, proof_id: Id }
ProbeMessage = { kind: "blabla_native_probe", schema_version: 1,
                 proof_id: Id, nonce: ProbeNonce }
ProbeResponse = { kind: "blabla_native_probe_response", schema_version: 1,
                  proof_id: Id, nonce: ProbeNonce }
SentProtocol = { kind: "probe", message: ProbeMessage }
             | { kind: "wake", message: Wake }
             | { kind: "work", message_sha256: Sha256 }
NativeToolSurface = {
  spawn_agent: { required: ["message", "task_name"],
                 optional: ["fork_turns", "model", "reasoning_effort"],
                 argument_type: "string" },
  list_agents: { required: [], optional: ["path_prefix"], argument_type: "string" },
  followup_task: { required: ["message", "target"], optional: [], argument_type: "string" },
  wait_agent: { required: [], optional: ["timeout_ms"], argument_type: "integer",
               timeout_ms_min: 10000, timeout_ms_max: 3600000 },
  followup_semantics: "may_queue_to_running_child_without_compare_and_send"
}
InitialIdleEvidence = {
  kind: "native_initial_idle", schema_version: 1, record_id: Id,
  spawn_evidence: EvidenceRef,
  completion: NativeToolObservation, status: NativeToolObservation
}
ProbeChallenge = {
  kind: "native_probe_challenge", schema_version: 1, proof_id: Id,
  coordinator: Child, capture_session: ProbeNonce, nonce: ProbeNonce
}
NonceRoundTripEvidence = {
  kind: "native_nonce_round_trip", schema_version: 1, record_id: Id,
  tool_surface: EvidenceRef, spawn_evidence: EvidenceRef, idle_before: EvidenceRef,
  challenge: ProbeChallenge,
  followup: NativeToolObservation, response: NativeToolObservation,
  status_after: NativeToolObservation
}
```

All literal arrays/strings in NativeToolSurface are exact, including parameter names, types and
required/optional sets. The coordinator captures this invocation-contract projection from the
currently exposed four native tools and their documented queue/wait behavior. It does not save
system/developer prompts, full tool descriptions, model catalogs, private reasoning or transcripts.
If an actual exposed signature/behavior cannot produce this projection exactly, record unavailable
and refuse this binding; do not omit a changed parameter or pretend CAS exists. The tool-surface
EvidenceRef file contains a NativeToolObservation with tool_surface projection. Its raw file SHA
is the existing NativeCapability.tool_surface digest used to derive host.version. The skill
compares the live invocation-contract projection with this captured surface before claiming each
host operation; different local collection IDs do not change the required surface equality.

The spawn_evidence file contains a NativeToolObservation with spawn projection and
operation_id null. The returned Child comes from that actual spawn result, not the requested
short name or child text; agent_id is null when absent. The requested name is recorded solely
to associate the call with its result, not to derive a canonical path. No spawn prompt, inherited
conversation, credentials or arbitrary metadata is stored. A status projection selects exactly
one actual list_agents entry by exact enrolled/probe task_name == agent_name; a duplicate or
ambiguous match is unavailable, and no matching entry is selected null. In source projections,
completion.origin.agent_id and SelectedStatus.agent_id contain only the ID actually exposed by
that notification/status, or null if omitted. After exact unique canonical-name correlation, the
normalized HostOutcome uses the immutable enrolled Child; a name-only source may be joined to
a separate ID already observed at spawn without claiming that the source exposed it. Any
non-null source ID conflicting with the stored identity is rejected; it cannot replace or enrich
that identity. Only an actual completed
status with its selected typed output marker can be projected as completed. A running or unknown
status never becomes idle from an expected marker or an old worker statement. On the observed
surface, actual agent_status string "running" maps to running; the single-key object
{"completed": TEXT} maps to completed only if TEXT strictly parses as the selected NativeMarker.
A plain historical "boundary-ready" string is not rewritten into a typed marker. Other shapes
are unknown/unavailable. These are source-to-projection rules, not invented platform fields.

The initial_idle_evidence file contains InitialIdleEvidence. The referenced spawn must match
Enrollment.spawn_evidence exactly; completion/status and spawn must name the same coordinator
and capture_session, have operation_id null, and have strictly increasing local_sequence in
spawn -> completion -> status order. Completion origin and selected status agent_name must both
match the actual returned Child, using the existing nullable-ID correlation rules. Both must
carry the same InitialReadyMarker, with run_id/task/acceptance_epoch exactly matching enrollment.
Core also reads the task and verifies it is currently ACCEPTED at that epoch. A marker attests
worker readiness only; it cannot replace the task record. The completed native notification plus
later completed selected status is the precise normalized meaning of initially idle. No literal
platform status named "idle" is required or invented.

The nonce_round_trip file contains NonceRoundTripEvidence. Its tool_surface ref must equal the
capability's ref and load the closed tool-surface record above. Its proof child is the actual
child in its own spawn_evidence; this harmless preflight child **need not equal an enrolled work
child**. Its idle_before file has the same InitialIdleEvidence shape, but both markers must be
ProbeReadyMarker with the challenge's proof_id. This proof-ready branch makes no claim that a
preflight child accepted a product task. It is permitted only for nonce proof, never as an
enrolled worker's initial readiness. All proof projections and challenge name the enrolled
coordinator; the tool-surface record must also name that coordinator.

The shipped helper exposes only this small local preflight constructor in addition to its
existing routes:

```text
new_probe_challenge(proof_id: Id, coordinator: Child) -> ProbeChallenge
```

It uses the OS random source to generate distinct fresh capture_session and nonce values before
collecting proof spawn/idle/followup/response records; neither is supplied in its input or taken
from model text. The host skill uses the emitted challenge unchanged, starts the harmless probe
child through the actual native spawn tool, obtains probe-ready completion plus status, and
sends exactly compact JSON ProbeMessage as the entire followup_task message. The child returns
only the matching ProbeResponse. This is a request-only nonce exchange with no advice, provider
inference or product work. `new_probe_challenge` calls no model tool. Capturing its JSON before
the tool calls and writing the final proof is ordinary helper I/O, not grant of run authority.

Proof validation requires all spawn/idle/followup/response/status_after observations to use the
challenge's capture_session and coordinator, and operation_id null. Their local_sequence order
is strictly spawn < idle completion < idle status < followup return < response completion <
status_after. The followup target equals the proof child's canonical task_name, sent is exactly
the challenge's ProbeMessage, and outcome is returned_without_error. The actual response origin
must independently match that same child; its ProbeResponse must match proof_id and nonce.
The later selected status must be completed for that child and carry that same ProbeResponse.
A wait_agent timeout/summary, echoed child-attestation name, unknown tool return or absent
completion cannot fill any of these fields. returned_without_error requires observing the actual
successful tool return; merely issuing or persisting a tool request does not establish it.
Ordering is coordinator-observed collection order,
not a claim about platform turn IDs or an atomic send. Successful transport return alone is not
nonce receipt, advice delivery or authentication.

The core validates every referenced file's exact bytes/hash/id/type and the cross-record
constraints above, with no recursive arbitrary evidence chain: a nonce proof refers only to its
tool-surface observation, spawn observation and initial-idle record; the latter refers only to
that same spawn. Reuse of an evidence path with a different expected kind/hash is rejected.
Files do not authenticate the coordinator; these are explicit local attestations within the
already stated cooperative trust boundary. The old native-boundary-proof/proof.json is historical
feasibility evidence only: it lacks these closed actual-capture records and must not be renamed,
wrapped or populated with invented fields to pass enrollment. Shipped helper/skill validation
requires a fresh actual capture in these forms. Other old capability blockers remain history.

The same NativeToolObservation type is the only ongoing HostResult.evidence payload. Its
operation_id must equal the pending HostRequest.operation_id (bootstrap null is rejected),
coordinator must equal enrollment, and its local collection sequence must not be reused for a
different observation in the same session. The helper's exact API is:

```text
normalize_event(request: HostRequest, observation: NativeToolObservation,
                evidence: EvidenceRef) -> HostResult
write_observation(observation: NativeToolObservation, path: Path) -> EvidenceRef
```

HostResult.request_sha256 and ClaimRequest.request_sha256 are the SHA-256 of the complete
HostRequest serialized with the evaluator's sorted-key compact UTF-8 canonical JSON convention;
they do not hash pretty-printed CLI stdout or a path. The same convention produces the exact
compact WorkContinuation/Wake/ProbeMessage text for tool dispatch; a sent work message_sha256
hashes those exact UTF-8 message bytes, without an added newline. These are transport identities,
not FNV revisions or authentication. `write_observation` validates the closed projection and
writes create-only canonical UTF-8 JSON plus one LF at the requested non-symlink project-relative
path. It returns id=record_id and SHA-256 of the exact saved bytes including that LF. Never
silently replace an earlier evidence file. `normalize_event` reads the referenced bounded bytes,
checks that hash/id and parsed-value equality to its observation argument, and then normalizes;
it cannot authorize a result using a separately supplied object that differs from the saved file.

The helper verifies only facts derivable from the HostRequest and saved observation: exact
operation ID, child/name fields, request/message hashes and the expected typed marker's available
key/nonce fields. It cannot itself establish enrollment or that a separate completion was already
observed. It maps inspect_child from status (completed with a request-bound typed marker -> an
idle candidate; running -> running; absent/unknown -> missing). It maps continue_work/wake_worker only from matching followup target,
exact sent content identity and returned_without_error; work identity is the SHA of the exact
submitted UTF-8 compact WorkContinuation message, avoiding storage of its brief again. It maps
await_boundary only from an actual completion projection whose origin matches request.key.child
and whose typed marker matches the request's available identity/expected-nonce fields. Completion notifications are not fabricated wait_agent results.
Explicit rejection, unknown outcome or unrecognized/missing source shape maps to HostOutcome
unknown with tool_error, missing_result or ambiguous_origin as appropriate; it never maps to
acceptance/completion. A no-call cancellation/deadline uses only the matching not_invoked projection and existing
HostOutcome.not_invoked result; its source is a coordinator attestation that the tool was never
called, not a native return. It must match the request's tool and operation ID and cannot count
as a successful proof step or clear possible prior exposure. The core repeats
operation/projection/key checks and verifies the enrolled coordinator, stored spawn identity,
separately observed matching completion/order, capture, acceptance epoch, generation and nonce
against its ledger before admitting a HostResult. It is the core that validates the idle candidate
against that prior completion. The helper's returned enum grants no admission or authority. NativeToolObservation contains no arbitrary worker Observation/source-kind fields.

`assignment_revision` is `task::revision::relevant_revision` with an empty identities map:
accepted task, scope, declared inputs/deliverables and task content. The `selected` revisions
are built by existing packet construction, including each binding's resolved identities. Both
are freshly rebuilt at capture, observation/admission, reservation and consume. Unrelated edits
stay irrelevant. The pre-work assignment revision never substitutes for a post-work selected
revision; section 5 defines the executable two-pass per-binding capture route.

The initial idle evidence includes the actual child completion notification after accepting its
BlaBla task and waiting for its first work brief, plus a matching non-running status inspection.
It is collected by the coordinator before enrollment and is not a claimed synthetic operation.
Enrollment uses sequence zero, `previous_sequence: null`, a fresh initial boundary nonce and
`checkpoint_id: "initial"` in operations that precede the first completed work turn. Sequence
zero is never submitted as an `ObservedEvent`. Completed boundaries start at one; subsequent
sequences must be exactly previous plus one. The checkpoint ID is core-generated from run,
task, epoch, generation, sequence and nonce. A worker cannot manufacture the next checkpoint
by choosing a larger sequence. Replacement acceptance, child or coordinator requires a new
run and enrollment; an old permit never follows it.

A generation covers one work continuation and its ensuing advice-only rendezvous. The
coordinator must not issue another work continuation while that rendezvous is unresolved.
After a resolved/no-advice boundary, the next authorized work continuation increments generation
under lock and gets a new nonce; checkpoint sequence remains monotonically increasing for the
run/task. An unexpected continuation invalidates the current generation rather than silently
advancing it. Actual host turn IDs are not required or fabricated: this tool surface supplies
no compare-and-send turn token.

## 4. Host-tool rendezvous: requests, results and executable routes

Every command described here is a proposed implementation interface, not available live
functionality. All repository BlaBla calls are argv beginning
`cargo run --quiet --bin blabla --`; a helper must not invoke a built or installed binary.

A host operation has this envelope:

```text
HostRequest = {
  schema_version: 1, operation_id: Id, key: BoundaryKey,
  created: Clock, deadline_boottime_ms: U64, payload: HostAction
}
HostAction =
  { kind: "inspect_child" }
| { kind: "continue_work", brief: Brief, brief_sha256: Sha256 }
| { kind: "wake_worker", wake: Wake }
| { kind: "await_boundary", expected_nonce: Nonce }
WorkContinuation = {
  kind: "blabla_native_work", schema_version: 1, key: BoundaryKey,
  brief: Brief, brief_sha256: Sha256
}
Wake = {
  kind: "blabla_native_wake", schema_version: 1,
  run_id: Id, checkpoint_id: Id, wake_nonce: Nonce
}
HostResult = {
  schema_version: 1, operation_id: Id, request_sha256: Sha256,
  key: BoundaryKey, evidence: EvidenceRef, payload: HostOutcome
}
HostOutcome =
  { kind: "child_status", child: Child, status: "idle" | "running" | "missing" }
| { kind: "continuation_accepted", child: Child }
| { kind: "wake_accepted", child: Child }
| { kind: "boundary_returned", origin: Child, marker: WorkerBoundary }
| { kind: "worker_response", origin: Child, response: WorkerResponse }
| { kind: "not_invoked", reason: "cancelled_before_call" | "deadline_before_call" }
| { kind: "unknown", reason: "tool_error" | "missing_result" | "ambiguous_origin"
                         | "deadline_after_call" }
WorkerStatement = { statement_id: Id, slot: "claim" | "proposal" | "evidence" | "attempts",
                    text: Text }
WorkerBoundary = {
  kind: "blabla_native_boundary", schema_version: 1,
  run_id: Id, task: Id, acceptance_epoch: Positive,
  child_attestation: Child, generation: Positive,
  sequence: Positive, boundary_nonce: Nonce,
  capture_id: Id, capture_sha256: Sha256
}
WorkerResponse = AdviceResponse | NoAdviceResponse
AdviceResponse = {
  kind: "blabla_native_response", schema_version: 1,
  run_id: Id, checkpoint_id: Id, request_id: Id,
  wake_nonce: Nonce, consume_nonce: Nonce, result_sha256: Sha256,
  child_attestation: Child,
  disposition: "acknowledged" | "declined"
}
NoAdviceResponse = {
  kind: "blabla_native_no_advice", schema_version: 1,
  completion: NoAdviceCompletion, child_attestation: Child
}
NoAdviceCompletion = {
  run_id: Id, checkpoint_id: Id, request_id: Id, wake_nonce: Nonce,
  refusal_nonce: Nonce, refusal_sha256: Sha256, code: Refusal
}
ConsumeRefusal = {
  kind: "consume_refusal", key: BoundaryKey, request_id: Id, wake_nonce: Nonce,
  refusal_nonce: Nonce, code: Refusal, exposure_attempted: false
}
```

The coordinator supplies `origin` by correlating the actual child notification/result with the
stored spawn mapping. It must not copy `child_attestation` into `origin`. A notification exposing
only the canonical task name can be joined to the unique enrolled spawn mapping; a status field
named agent_name is usable only when its actual value exactly equals that canonical task_name.
A missing, ambiguous or different name is `unknown`/rejected regardless of a null agent_id.
The normalized Child repeats the immutable enrolled identity, including null when no separate
ID was observed; a source that exposes a conflicting separate ID is rejected, never overwritten
from worker text. A name-only match does not establish platform authentication. The single
coordinator, generation/nonce checks and cooperative limits are unchanged. Raw host evidence contains only the tool
name, submitted bounded arguments and relevant returned metadata or selected response marker,
not the transcript. Its local evidence ID/path is coordinator-assigned, not claimed to be a
platform request ID. Raw unknown fields are never used as authority by the normalizer.

Worker inputs are exclusively `WorkerStatement`, never existing `Observation`. They have no
`kind`, `capture`, `observed_revision` or `fact` fields; supplying any is invalid input. Even the
`evidence` slot means a worker statement about evidence, not a deterministic observation. The
core alone constructs `Observation` with `kind: worker_statement`, `fact: null` and fixed
`capture: host:native-worker-statement`; observed native origin establishes who said the text,
not whether it is true. Coordinator-observed identity/status/transport metadata stays in the
separate closed `HostOutcome`/receipt records. This binding does not inject those as free-text
HostObservation or ExpertInference context. Deterministic task/evidence/memory observations
come only from the existing local packet collector. There is no native route accepting arbitrary
Observation arrays, including via a direct experimental checkpoint event.

Permitted request/result pairs are exact: inspect/child_status; continue/continuation_accepted;
wake/wake_accepted; await/boundary_returned or worker_response. Any action may yield not_invoked
or unknown. `await_boundary` knows from the current state which of its two results is valid.
A request hash, key or pair mismatch is rejected without advancing state.

Each is a thin call to the identically named `expert native` subcommand with the same flags and

is read-only and returns a pending request; it does not execute a tool or mark it completed.
`host-claim` atomically marks that exact request dispatch-started before the skill calls a tool.

`start-run` follows enrollment and reads the exact frozen `NativePlan`/protocol referenced in
section 11. It verifies this arm's initial identities/snapshot and stores its complete immutable
runtime config and limits as a run-bound payload before the authoritative ledger points to it.
It returns `AdvanceResult`; an exact repeated start resumes the stored run, never resets it.
An advisory run waits for explicit issue rather than manufacturing its permit.

`advance` computes the next operation from authoritative state, not a caller-supplied action.
It creates at most one pending host operation per child. Before first work it requests inspection,
then `continue_work`, then `await_boundary`; a completed boundary requests fresh inspection,
then returns `checkpoint_due` for `observe`/checkpoint evaluation. A captured actionable proposal
can enter prepare-wake; silence/abstention advances to the next approved work continuation.
After dispatching a wake, advance requests an awaited response. The frozen brief defines the
completion criteria; the captured `final_boundary` is a worker attestation. `arm_finished` requires the final
worker completion and every resulting checkpoint/rendezvous to be settled, not mere absence of
a next host request. It means host execution ended; independent grading may still be unavailable,
so the evaluator can still report that arm incomplete. Duplicate advance returns the same pending
operation. `host-result` returns `HostRecordResult`. The operation factory creates deadlines and
keys under the same ledger transaction. Neither start nor advance invokes model tools.

The native skill performs these exact model-tool steps, never through Python:

1. `inspect_child`: call `collaboration.list_agents` with the enrolled task-name prefix and
   select the exact enrolled child. Normalize idle only from an actual completed selected
   status and the matching observed completed-turn marker under section 3's rules. Unknown
   states are missing
2. `continue_work`: call `collaboration.followup_task` with the enrolled target and exactly a
   compact JSON `WorkContinuation`, built from the request key and frozen brief. It tells the
   worker to use that generation/nonce and return the next sequence (`key.sequence + 1`). The
   brief requires the worker to call `capture-boundary` after its last edit/check, then return
   the emitted `WorkerBoundary` marker unchanged and perform no further task-affecting work.
   The accepted BlaBla task remains ACCEPTED, never READY merely to pause
3. `wake_worker`: call `collaboration.followup_task` with the enrolled target and exactly the
   compact JSON `Wake` as the entire message. It contains no result, policy hint or advice
4. `await_boundary`: wait for the corresponding native child notification, using
   `collaboration.wait_agent` if needed; normalize the actual notification and matching marker.
   A timeout/wake without that notification is still pending, never a completed child result

`followup_task` may queue into a running child. A prior idle lookup is not atomic with that
call. Therefore only the advice-free wake may race; the cooperating worker must run `consume`
as its first task-affecting action in that wake turn, before edits, checks or another turn's
work. It must refuse if it has already advanced, received another work instruction or cannot
identify the expected wake. This is an explicit cooperation obligation, not enforced access
control. An independently observed violation invalidates the generation. Unobserved violations
cannot earn completeness credit.

### Post-work capture and per-binding revision projection

`capture-boundary` is executable by the cooperating worker after its last edit/check and before
returning control. It validates the claimed continuation/work key against the exact ledger
operation, accepted task/epoch/child/generation and nonce. It intentionally allows scoped work
to have changed the pre-work revision. It reads the current task and tree itself, chooses the
next sequence/checkpoint ID, and performs this transaction under the standard locks:

1. Snapshot the post-work assignment revision and accepted task evidence. Build the common
   event with current recorded clock, `kind: turn_end`, the next sequence and **empty observations**
2. Select eligible bindings using the existing role/checkpoint/priority/judgment-budget rules.
   For each selected binding call existing `project::expert::build_packet` with that empty event
   to obtain its actual `RelevantRevision`. This initial build is for revision selection only;
   missing proposal/claim context is not treated as a completed actionable packet
3. Construct a separate Observation array for each binding from the same frozen WorkerStatement
   values. Core IDs are `native-statement-` plus `packet::digest((capture_id, statement_id))`;
   duplicate statement IDs are invalid. Kind/capture/fact are fixed as in section 4; set each
   observation's `observed_revision` to **that binding's** first-build revision fingerprint
4. Build that binding's packet again using an event with exactly its projected observations.
   Require byte-equal first/second `RelevantRevision`. Store its revision, observation array and
   packet hash and exact bounded packet history in `BindingProjection`. Required context still
   missing/unknown/truncated remains so; stamping asserts freshness of a captured worker
   statement, never its truth
5. Re-read the assignment/evidence and all selected revisions. If any differ from the sampled
   values, refuse `stale_revision` without publishing a marker. Otherwise durably save the
   immutable `BoundaryCapture` and its hash, then emit only its `WorkerBoundary` marker

`capture-boundary` returns an identical marker for an identical repeated capture of the same
work operation; changed statements or post-work revisions cannot replace that capture. A failed
capture with no durable record may be retried before returning the turn. A successful capture
is pending evidence, not an observed host boundary or permission to evaluate. The worker must
return that marker as its completed-turn result without further work. External editors are not
locked by this cooperative protocol; observation, admission and consume rechecks remain required.

`observe` consumes the actual coordinator-correlated completion marker and subsequent idle
result. It requires their capture ID/hash, child, task, epoch, generation, sequence and nonce to
match the stored capture. Rebuild each packet with its stored bounded history and **stored**
binding-specific observations and require equality with the captured revision and packet hash, as well as current assignment
revision/evidence. Never restamp an old capture to a newly observed revision. It returns
`boundary_observed` only after these checks. A mismatching post-capture edit is stale and cannot
be hidden by the worker copying a fresh fingerprint.

The single ledger checkpoint event has empty observations and the common EventStamp; each
`BindingProjection` shares that exact stamp. `expert checkpoint --experimental-run RUN` requires
its input event to equal that core-owned event and refuses nonempty caller observations. During
its binding loop it loads **only** the selected binding's saved projection, rebuilds via the
existing packet builder, and requires the captured hash/revision again. It must not concatenate
observations from incompatible bindings: current `build_packet` would poison a slot upon the
other binding's fingerprint. Existing `advance_checkpoint` tracks the common event; existing
trace `rebuild` uses the per-binding packet's own observations and the same freshness rules.
Bindings omitted by budget are recorded as omitted; no phantom projection or inference is added.
This is a required bounded checkpoint-path change, not a capability already supplied by current
Observation validators.

`prepare-wake` requires its proposal binding in `checkpoint.selected` and uses the existing
proposal record, not a supplied `ExpertResult`. An empty selection can only abstain. Under the run
transaction it revalidates scope/revision/authority, reserves the delivery and suppression key,
and persists one wake operation and nonce. It returns no template. Silence/abstention has no
reservation, no wake and zero delivery units. Only one proposal per checkpoint may reserve. A missing/non-actionable result settles the
boundary with no advice; it does not leave a pending wake awaiting an impossible proposal.

The state progression is `enrolled -> boundary_observed -> request_reserved -> wake_requested
-> consumed -> response_observed`. A no-advice boundary is settled without request_reserved;
its disposition is stored separately, and advance may finish or schedule the next generation.
`wake_requested` means dispatch-started, not delivery. A wake
may arrive before its tool result has been persisted: consume is allowed after dispatch-started
with the exact persisted nonce; it does not require a possibly late transport acknowledgment.
A `wake_accepted` result never advances to consumed or delivered.

`ConsumeRequest` deliberately carries the advice-free wake and the worker's known enrollment
identity. The nonce resolves exactly one immutable reservation in the ledger, which supplies
its full `Checkpoint`, request ID and selected revisions. The worker need not obtain unknown
post-turn packet hashes to consume. This is still bound to the complete tuple; no caller-provided
revision or identity may replace the stored one.

`consume` obtains the locks in section 8 and rechecks the actual current ledger, task/epoch,
assignment and selected revision, checkpoint, generation, reservation, nonce, deadline,
revocation and permit scope. An eligible first consume commits its nonce, exact serialized
result hash and irrevocable exposure-attempt marker before writing the fixed result to stdout.
No earlier native reservation command or wake output contains that result. Trace inspection by
the coordinator remains available; the host skill must not forward those inspection payloads
to the worker. A second consume after possible exposure returns
`no_advice/already_consumed` with `completion: null`; it never returns the saved template or
certifies non-exposure, even to the same caller.

A process cannot atomically commit a file and prove that a model saw stdout. The pre-output
commit is the at-most-once exposure boundary; a crash/output error after it is unknown, not
confirmed delivery. The worker's actual tool result supplies the consume nonce/hash; the
coordinator then correlates its `WorkerResponse` with the native response origin. A receipt
lost after possible exposure suppresses redelivery permanently for that reservation.

### Request-bound no-advice completion

If consume resolves the exact wake/reservation and matching enrolled child but refuses **before
any exposure commit**, it atomically stores a `ConsumeRefusal` with a fresh nonce and the
original key/request/wake IDs. Its `refusal_sha256` hashes that complete canonical record;
NoAdviceCompletion is its exact projection plus hash, and the outer result code must match it. It returns `no_advice` with `NoAdviceCompletion`, without a consume nonce,
ExpertResult or advice. Identical repeat requests may return the same negative completion;
no new reservation, charge or exposure is created. This branch records `consume_refused` and
continues awaiting the actual native worker turn completion.

The worker returns `NoAdviceResponse` containing that completion unchanged. `await_boundary`
accepts it through its WorkerResponse union; `record-response` correlates actual origin and
requires the exact persisted refusal hash/nonce, request/wake/key and no exposure commit.
It matches the original captured key, not a fresh replacement revision; receipt reconciliation
never authorizes delivery and may occur after revocation/expiry. It then records `not_exposed`
with `reason: consume_refused`, settles the wake turn and suppresses
that reservation forever. No acknowledgment or delivered count is fabricated. Only now may
advance act again. A pre-reservation silence/abstention needs no wake or negative worker response
because its original completed work boundary has already been observed.

`stale_revision`, `missing_context` and `non_actionable` refusals may settle normally and allow
advance to issue a fresh generation **if** all current task, frozen-control and run checks still
pass. Other refusal codes stop the arm after reconciliation; their negative completion provides
non-delivery evidence, not permission to continue. Expiry/revocation does not renew the permit.
If the wake cannot be resolved, the child mismatches, a consume might already have exposed, or
storage/clock uncertainty prevents a trustworthy refusal commit, return `completion: null`
(or exit 4 for I/O) and retain unknown/stopped status. The worker cannot invent a negative token;
absence of that token leaves an honestly incomplete arm. A missing actual response after a
persisted refusal also leaves host completion unobserved; advance never guesses the child is idle.

For an `AdviceResponse`, record-response requires matching origin, all nonces, request/result
hash and the recorded consume, then records acknowledgment or decline. For `observed_resolution`,
it reads current task evidence and applies section 6's shared deterministic correction checks;
worker text cannot supply those facts. A worker that merely echoes a wake cannot acknowledge
advice. A matched advice or permitted negative response can allow the next generation; an unknown
exposure stops the experimental run. No response deadline can be extended. Invalidation removes
unexposed eligibility while preserving counters, reservations and uncertain suppression.

Refusal codes are the closed set:

```text
Refusal = "invalid_input" | "identity_mismatch" | "epoch_mismatch" | "origin_mismatch"
        | "generation_mismatch" | "sequence_gap" | "task_not_accepted"
        | "stale_revision" | "stale_checkpoint" | "unsupported_capability"
        | "permit_missing" | "permit_mismatch" | "permit_revoked" | "expired"
        | "clock_uncertain" | "budget_exhausted" | "already_claimed"
        | "already_consumed" | "duplicate_delivery" | "uncertain_delivery"
        | "missing_context" | "non_actionable" | "runtime_changed"
        | "storage_missing" | "storage_corrupt" | "ledger_exhausted"
```

Unknown IDs and replayed old keys are refused. A valid abstention/refusal is exit 0; malformed
wire/config is exit 2 and I/O/durability failure exit 4. No exit status changes ordinary task or
project completion. A caller must inspect the tagged result, not equate exit zero with advice.

Transport acceptance and exposure attempt project to core `Unknown`; neither claims a worker
read the message. A matching acknowledgment/decline establishes receipt and projects to the
corresponding core state; evaluation counts this as an observed delivery and separately counts
acknowledgments/declines. The native binding does not invent a standalone `Delivered` receipt
from a successful `followup_task`. `ObservedResolved` still requires the current deterministic
check/evidence identity and changed corrective state tested by existing `receipt()` logic.
It does not by itself prove causation or general usefulness.

`not_exposed` is legal only if the authoritative ledger proves exposure was never committed.
For `consume_refused` its refusal hash is required and must match the correlated NoAdviceResponse;
for the other two reasons it is null.
It may close a pre-consume reservation as core `Proposed/no_delivery_verified`; its budget
unit remains spent and the same reservation is never reused. It cannot clear a consume-unknown
entry, and lack of an acknowledgment is not evidence of non-delivery. Ordinary receipt CLI
cannot manufacture experimental receipts: those use the run-bound native operation, with
experimental identity retained. New observations do not overwrite an older checkpoint to
inject receipts; native receipts are attached directly to the reserved checkpoint under lock.

permit and for the permit attachment to its already initialized run. An identical repeated issue returns the original

require revocation and a new run/permit with fresh explicit approval. Revoke is idempotent,
records its first reason/evidence, invalidates all unconsumed generations in the same commit,
and never resets counters or removes uncertain suppression. It prevents new admissions and
consumes; a provider already in flight can finish only into a non-deliverable trace. A response
can still be reconciled after revocation, but cannot trigger another consume.

Provider certification for advisory remains required through `require_mode(Advisory)` plus the
actual local smoke evidence. A permit removes only the need for prior production promotion in
this isolated experiment; it does not remove provider, policy, context, freshness or host checks.
It cannot be parsed as a `PromotionRecord`, added to `RuntimeConfig.promotions`, or silently
converted into one. Even an expanded experimental run has `promotion_eligible: false` for its
permit; independently graded observations may inform a later, separately reviewed production
assessment. This schema grants no promotion path to the cooperative host.

## 8. Durable accounting, locks, clocks and restart

The authoritative transaction file is `.blabla/expert/ledger.json`; the create-only
initialization marker is `.blabla/expert/experimental.initialized`. Extend its closed `Ledger`
with an `experimental_runs` map keyed by run ID. Each run stores its immutable issued permit
(if advisory), frozen run identity, enrolled children/generations, last trusted clock, stopped
reason, counters, provider-attempt records, native operations, reservation/consume records and
receipt references. Existing common suppression `entries` remain in this same file and gain a
required `execution` tag. Experimental scopes cannot evade ordinary uncertain-delivery
suppression by changing run IDs. Experimental receipt history cannot become production evidence.

All authorization-relevant state changes take locks in the existing order: task-store lock,
then `.blabla/expert/.store.lock`. The latter is also the run lock; there is no independent
Python lock/database that can authorize a concurrent consume. Native-operation claim, issue,
revoke, provider reservation, delivery reservation, consume, invalidation and receipt reconciliation
each read/validate/mutate/replace the entire authoritative ledger once under that lock. No
multi-file rename is called a transaction. Helpers inside an already locked transaction must
not recursively acquire the same locks.

Write a unique same-directory temporary file, flush/sync it, atomically replace the ledger,
then sync the containing directory before returning authority or exposing text. Any write,
rename or durability ambiguity fails closed. Do not send a tool/provider request or emit advice
before a successful durable reservation. The initial ledger is created explicitly during first
experimental enrollment only if no experimental run directory/initialization marker exists;
enrollment atomically creates a durable create-only marker before the first ledger write.
Once that marker exists, absence of the ledger is `storage_missing`, never an empty budget.
A crash between marker and initial ledger is a blocked initialization, never an automatic
reset. Corruption,
unknown schema or limits overflow stops the run, preserving files for investigation.

Experimental payloads live in `.blabla/expert/experimental/RUN/traces/` and bounded host evidence
in `.blabla/expert/host/native/RUN/`. Payloads are synced before a ledger transaction refers to
them; an orphan can be deleted later, but an index or trace file can never authorize an action.
The existing `index.json` is a rebuildable projection. The ledger retains immutable permit and
operation/consume identities plus suppression tombstones when payloads expire. Trace deletion
and terminal-task cleanup must not refill or erase live/unknown experimental accounting. A
missing required payload refuses further delivery, rather than reconstructing permission from
a caller-supplied copy. Fixed ledger-size exhaustion abstains instead of evicting safety state.

Budget units and charging points are fixed:

- `provider_attempts`: one external `CommandProvider` single/batch invocation, charged before
  spawn. A batch of up to four questions costs one attempt and its number of questions. Local
  readiness HTTP traffic inside the existing adapter is not another inference invocation
- `evaluated_questions`: number of requests in that invocation, charged in the same transaction
- `delivery_attempts`: one request reserved for potential exposure at prepare-wake, charged with
  the common suppression entry. Decline, timeout, invalidation and lost receipts do not refund
- `max_wall_ms`: elapsed `CLOCK_BOOTTIME` milliseconds from issue/run start, including waits,
  inference and suspend. Not a sum of completed calls and never paused by process exit

Experimental retries are exactly zero (`limits.retries == 0`); concurrency is one. This avoids
hidden provider retries bypassing persistent accounting. A provider reservation is dispatch-started
before launch; an uncertain crash burns the attempt and questions, with no replayed launch.
The same rule applies to claimed native continuations/wakes. Exact stored results can reconcile
unknown state; a new response cannot pretend that the original dispatch never happened.

The first implementation supports this experimental path on Linux only, using the existing
`libc` dependency for `CLOCK_BOOTTIME`, `/proc/sys/kernel/random/boot_id`, and `SystemTime` UTC.
This is a scoped support decision, not a claim that current ordinary Windows tests fail. If
clock/boot identity or durable directory sync is unavailable, experimental admission is refused.

At every transaction require the same boot ID, nondecreasing boottime and nondecreasing UTC;
require the absolute difference between elapsed UTC and elapsed boottime since the preceding
sample to be at most 2,000 ms. A larger change, backward clock, overflow or unreadable clock is
`clock_uncertain` and stops the run. The 2,000 ms check is a discontinuity detector, never extra
expiry allowance. Admission requires `not_before <= now < expires` and elapsed time strictly
less than `max_wall_ms`. The effective action deadline is the minimum of the operation/provider
timeout, permit expiry projected onto the current monotonic sample, and remaining run wall
budget. Deadlines are persisted once and cannot slide on poll/retry.

After a helper/runner process restart, read the same ledger and clock before doing anything.
Pending, never-claimed operations can resume with their original deadlines. Claimed operations
without a recorded result are unknown and must not be issued again. Consumed-without-response
remains unknown and never exposes text again. A new OS boot invalidates the run. Loss/replacement
of the enrolled coordinator also stops it; a replacement cannot simply reuse its textual ID.
No stale-lock deletion, empty-ledger fallback, permit reissue or elapsed-time grace refills a run.

## 9. Admission at checkpoint, reserve and consume

Experimental execution is explicit on the CLI:

```sh
cargo run --quiet --bin blabla -- expert checkpoint --event event.json --experimental-run RUN --json
cargo run --quiet --bin blabla -- expert replay trace.json --json
```

`--config` may be omitted only with `--experimental-run`; the core then loads that run's
immutable frozen configuration internally. If supplied explicitly for an experimental run, its
exact bytes must match the frozen configuration. Ordinary checkpoint retains its existing
required-config behavior. The helper must not guess internal payload paths to obtain configuration.

Experimental checkpoint must not call the current singleton `store.set_runtime(config)` or use
`.blabla/expert/runtime.json` as its authority: its immutable per-run config is loaded from the
run-bound payload. Ordinary behavior keeps its existing runtime file. Factor shared checks to
accept the selected config explicitly, so one concurrent arm cannot replace another's settings.
Experimental histories contain only that experiment's records; shared uncertain suppression is
still checked conservatively across runs and execution kinds. Trace listings retain the tag.

The native `handle_checkpoint` operation invokes checkpoint only after `observe`. The following
order is normative and must be tested at both seams:

1. Before any provider construction/dispatch, resolve `--experimental-run` from the ledger,
   require the current recorded native checkpoint, immutable run/config identity and current
   accepted task/epoch, then validate clock, revocation, scope, capability, frozen input baseline,
   real calibration and policy. Read current revisions through the same existing packet builder
2. Off exits with exactly zero provider calls. Shadow uses the enrolled run's frozen limits and
   actual provider with no delivery authority. Advisory additionally requires the matching issued
   permit. Missing/invalid permit does not fall back to an unaccounted shadow inference
3. Immediately before every compatible single/batch dispatch, recheck the run and charge attempts
   and questions atomically. Release the lock during inference. A provider late result is stored
   as an observed failure/stale result; it cannot reverse revocation, expiry or generation changes
4. Create traces using existing response validation, expertise-pair handling, `policy::decide`,
   deterministic precedence and `check_current`. For this run choose experimental authority only
   through `pilot::admission`; ordinary calls still use unchanged `promotion_matches`. Never call
   `promotion_matches` and then force its Boolean true for a permit
5. At prepare-wake, factor the existing reserve gates into one locked routine: local provenance,
   execution/config identity, replay, actionable result, rebuilt selected revision, current
   checkpoint, shared deduplication/unresolved limits and exactly one delivery per checkpoint.
   Its final authority branch is ordinary promotion OR exact experimental permit, never both
6. Persist common suppression plus delivery charge plus wake request in the same ledger commit.
   Unlike ordinary `DeliveryProposal`, this reservation returns no `ExpertResult.message`
7. At consume, repeat all freshness/authority/runtime checks against current data and that exact
   reserved key. Verify no other exposure committed; do not reject this request merely because
   its own reservation is `Unknown`. Other uncertain concerns still suppress it. Validate permit
   again without charging twice, then atomically commit the sole exposure attempt before output

The initial frozen task snapshot is checked before starting each arm. Legitimate scoped work
changes that snapshot during the arm; such changes are checked through current relevant revision,
not prohibited by comparing all current task files with the initial bytes forever. During the arm,
`snapshot_change` means changes to frozen controls, protocol/calibration/provider/binding inputs
or unapproved baseline replacement, not an authorized edit to a task deliverable.

Ordinary `expert delivery` and `expert receipt` reject any experimental trace/request. Experimental
commands cannot read production promotions as their permit. `expert evaluate` imported packets
remain shadow-only and cannot acquire local provenance by supplying an experimental run ID.

### Frozen protocol input to the pure fitter

`protocol_evidence` names the complete frozen evaluator protocol JSON, using the existing
closed `validate_protocol` schema in `experiments/expert_eval.py`; it is not an independently
authored subset or a claim that validation already succeeded. `EvidenceRef.sha256` for protocol,
plan and manifest is the SHA-256 of the exact file bytes. `FitPlan.protocol_sha256` remains the
evaluator's **canonical parsed-document** fingerprint, so whitespace can change the former
without changing the latter. The two hashes have different roles and must not be interchanged.

The concrete Rust API is:

```text
validate_fit_context(
    request: &FitSavedRequest,
    protocol_bytes: &[u8],
    plan_bytes: &[u8],
    manifest_bytes: &[u8]
) -> Result<ValidatedFitContext, TraceError>

fit_saved(
    request: &FitSavedRequest,
    context: &ValidatedFitContext
) -> Result<FitSavedResult, TraceError>

ValidatedFitContext {
    request_fingerprint: Sha256,
    protocol_fingerprint: Sha256,
    development_manifest_sha256: Sha256,
    holdout_manifest_sha256: Sha256,
    candidate_thresholds: Vec<FiniteProbability>,
    budgets: BTreeMap<FitFamily, FitProtocolBudget>
}
FitFamily = GoalDrift | Expertise | ClaimSupport | FailedApproach
FitProtocolBudget {
    false_nudge_max: FiniteProbability,
    min_evaluable_coverage: FiniteProbability,
    min_justified_opportunities: Positive
}
```

These last three types are in-memory types, not another wire schema. ValidatedFitContext has
private fields, no Deserialize implementation and no unchecked/public field constructor;
`validate_fit_context` is its only constructor. The validator and fitter are pure: no file or
network I/O, provider calls, subprocesses, trace writes or delegation to Python. A bool, hash
string or caller-constructed map cannot substitute for this value.

`expert fit-saved --input FILE` strictly parses the bounded FitSavedRequest, then reads the
three project-relative EvidenceRef paths through existing non-symlink bounded-file rules.
Each file is at most 8 MiB. The CLI passes those bytes, unchanged, to `validate_fit_context`,
then calls `fit_saved` with its returned value. It must not call the fitter with a deserialized
context or skip the validator because Python previously validated the protocol. `calibrate-live`
sets protocol_evidence from the exact same PROTOCOL file used before inference; it cannot
substitute another file during fitting. Other callers of the pure Rust API supply the bytes
explicitly and use the same constructor.

The pure validator performs all of the following before returning a context:

1. Hash each exact byte slice and require equality with its corresponding protocol_evidence,
   plan_evidence or manifest_evidence SHA. Strictly parse UTF-8 JSON with duplicate-key,
   unknown-field, wrong-type, non-finite-number and trailing-content rejection. Parsed plan and
   request manifest must equal the embedded `request.plan` and `request.request_manifest`
2. Validate the complete protocol's existing closed field shape and semantic constraints from
   `validate_protocol`, including schema_version 1, frozen status, nonempty approved_by,
   exactly the four family budget keys, development-only calibration and holdout_access false.
   Validate the existing budget/threshold numeric types and ranges, not just their presence.
   This validates frozen protocol data; it does not authenticate the owner or authorize delivery
3. Compute SHA-256 over the **whole** parsed protocol using the evaluator's sorted-key compact
   UTF-8 canonical serialization, including its number/string serialization rules. Require exact
   equality with `request.plan.protocol_sha256`. A cross-language canonicalization mismatch is
   invalid input; do not fall back to file SHA, ignore fields or hash only the fitted subset
4. Require protocol datasets.development.manifest_sha256 to equal both plan and request-manifest
   development hashes, and protocol datasets.holdout.manifest_sha256 to equal the plan's
   holdout hash. Verify `plan.request_manifest_sha256` against the canonical embedded request
   manifest. No holdout data file is opened by any of these comparisons
5. Extract candidate_thresholds and the three named objective fields for **each** family directly
   from that validated protocol. Compute request_fingerprint over the complete canonical
   FitSavedRequest, sealing this context to its exact embedded candidates, objectives, inputs
   and EvidenceRefs. It is a consistency seal, not authentication

Before scoring, `fit_saved` recomputes the request fingerprint and requires the seal to match.
For every candidate probability-rule threshold, require exact numeric membership in the
validated protocol's candidate_thresholds, with no rounding band or nearest-value replacement.
For each group, resolve its exact FitFamily and require objective.false_nudge_max,
objective.min_evaluable_coverage and objective.min_justified_opportunities to equal the validated
family budget fields exactly. `min_proposed_nudges` remains the positive floor frozen in the
fit plan; it is not read from the distinct held-out min_delivered_nudges field. The fixed rank
order remains unchanged. A request that fails any comparison returns invalid input before
candidate scoring and produces no selected policy. The policy's 0.001 uncertainty band applies
to runtime answer decisions only, never to these frozen-input identity checks.

### Exact candidate policy mapping

Each candidate contains complete concrete existing `PolicySettings`, including rule order,
predicate, template, reference selection and `CalibrationRecord`; no scalar signal is interpreted
as a universal probability. All candidates in a group have identical provider, binding,
question/template/development fingerprints and rules. Only their predeclared probability-rule
threshold values and identifying calibration record IDs may differ. Every threshold value must
be in frozen protocol `calibration.candidate_thresholds`. Both threshold keys and policy
fingerprint must pass the existing core `validate_settings`/`policy_fingerprint` checks.

For the shipped judgment families, the allowed varied predicate is fixed as follows:

- goal-drift uses `ChoiceLabel { label: "drift" }`; it has one threshold-free candidate. Choice
  probabilities are retained provenance and do not become a threshold policy
- claim-support varies the threshold of `NoulProbability { value: false }`, so the core tests
  the probability of non-support rather than silently using the positive proposition
- failed-approach varies `ScoreTail { from_level: "repeating" }`, using the current ordered
  distribution tail. A scalar expectation is not substituted
- expertise uses primary `expertise-useful` with `NoulProbability { value: true }` and a fixed
  selection PolicySettings for `expertise-selection`. Selection is a paired Choice result, never
  an independent actionable candidate or a probability threshold

Other fixed rules in each full candidate remain exactly as frozen and type-validated. A
Boolean-only/level-only provider cannot satisfy these probability predicates by inventing a
number: current policy returns `missing_answer_statistic`. Threshold-free variants for another
provider require a separately frozen fit plan, not an operator switch during this fit.

The `FitObjective` false-nudge ceiling, coverage floor and justified-opportunity floor must equal
the frozen protocol's matching family budget. `min_proposed_nudges` is an explicitly frozen
positive development floor; absence is invalid, not a guessed default. It and the fixed rank
order are part of the fit-plan hash. This is development feasibility only, not a held-out
confidence bound or production promotion. An insufficient development set honestly yields no
feasible candidate rather than relaxing its declared objective after the results.

### Core scoring and deterministic fitting algorithm

`expert fit-saved` validates the protocol/plan/manifest byte context and exact bindings above,
then validates every packet/definition/response with existing core validators before this loop:

1. For each candidate and assigned development case, select the primary request/response by
   exact ID. Require the candidate calibration provider, question/template/development and
   policy fingerprints to match the recorded inputs. Construct an in-memory `TraceRecord::new`
   with that candidate, `mode: Shadow`, `provenance: Imported` and the saved request's history.
   It does not accept a caller-supplied ExpertResult or pretend imported case facts are local
   deterministic observations. Runtime deterministic blockers still bypass semantic inference
2. For expertise, require exactly the paired usefulness/selection requests and validated
   responses, with the same context/candidate list accepted by `validate_batch`. Attach the
   existing `ExpertisePair` and call existing `apply_expertise_pair`. Use its primary result,
   including `expertise_none`, selection failure, unknown reference and useful-question silence.
   Do not count the selection question as another nudge/opportunity. No invented batch execution
   or shared provider usage is recorded; pairing here is deterministic saved-response scoring
3. For ordinary cases, use the constructed record's result. These operations call the same
   `policy::decide`, predicate matcher, renderer, unresolved-history suppression and paired
   expertise logic as runtime. In particular, `abs(probability-threshold) <= 0.001` abstains,
   threshold comparison is strict `>`, false Noul uses `1-p`, and Score uses its ordered tail.
   Python's fixture `probability >= threshold` path is never used
4. A proposed nudge is result `nudge` or `escalation`. It is correct only if independent gold
   says justified and the set of emitted references equals one frozen acceptable reference
   set. Wrong-target nudges count false and also miss the justified opportunity. Every justified
   case without a correct proposed nudge counts missed, including abstentions/failures. Planned
   is all assigned cases; evaluable counts valid silence/nudge/escalation results, not abstentions
5. Feasible requires proposed >= its frozen positive floor, justified >= its frozen floor,
   false_proposed / proposed <= false_nudge_max, and evaluable / planned >= coverage floor.
   Zero denominators are infeasible. Among feasible candidates select the lexicographically
   minimum `(missed_correct, false_proposed, candidate_id)`; all share the same case population.
   Return its exact frozen PolicySettings, not newly generated rules or thresholds. With no
   feasible candidate return null selected fields and `no_feasible_candidate`

A provider failure is an observed failure response and may reduce coverage; a missing execution
record is an incomplete calibration and cannot be fitted by dropping that case. Fit errors return
exit 2 (invalid input) or 4 (I/O) without selection; a valid no-feasible result is exit 0. Store
all candidate CaseDecisions and counters so independent review can replay the exact selection.
Implement this bounded pure fitter in `src/expert/calibration.rs`, registered from `mod.rs` and
called by `src/cli/expert.rs`; reuse TraceRecord/ExpertisePair instead of copying policy semantics.
Include its `calibration` implementation fingerprint alongside existing core fingerprints.

The calibration execution config and later advisory runtime config need not have the same
whole-file hash: fitting produces the latter's selected policies. At issue require exact provider
identity/argv, request limits and question/template identities from actual calibration, and require
advisory policies byte-equal to the selected core fitter output. Preserve both config hashes and
the fit plan/result hashes; no config contains its own eventual calibration output hash. A fit
can be eligible for some groups only; a permit may name only selected groups and must include
both expertise members together. If none qualify, emit `no_feasible_policy` and keep delivery
blocked. An incomplete output has null fitted_result and no selected settings; eligible and
no_feasible_policy require a non-null validated core fit result. Fixture calibration, scalar scorers and a renamed saved-answer file cannot satisfy this
real-calibration identity. Freeze the output before any held-out or matched-arm observation.

- Rename the historical feasibility proof to the nonce proof path: missing kind/closed projections,
  rejected. A fresh helper challenge requires fresh actual probe tool/notification captures
- Use an initial-idle status from before its completion, a different child, mismatched marker or
  wrong task acceptance epoch: rejected, even if both messages contain the word ready
- Use list_agents agent_status running, an unknown status, duplicate matching names or a
  wait_agent summary as completed/idle evidence: unavailable or rejected, never idle
- Omit a newly exposed tool parameter from the captured NativeToolSurface or change followup
  semantics to claim CAS: unsupported surface, rejected before enrollment/action
- Change response origin, proof_id, nonce, sent target, coordinator or local observation order in
  the four-file graph: rejected. A correct echo from another child cannot satisfy the proof
- Forward an ongoing observation with null/different operation_id, mismatching saved-file hash,
  or changed in-memory projection: rejected before HostResult recording
- Add `"kind":"host_observation"`, `"fact":null` or `"observed_revision":"..."` to a
  WorkerStatement: unknown field, rejected. Origin correlation cannot upgrade its source label
- Capture a statement after editing a deliverable: projection uses the new per-binding revision,
  not the WorkContinuation's old assignment digest. A further relevant edit before observe
  rejects the whole capture as stale; no automatic restamp can conceal it
- A FitSavedRequest omitting protocol_evidence is invalid. A protocol file whose raw SHA differs
  from protocol_evidence.sha256 is invalid even if its parsed budgets look plausible. A matching
  raw file SHA with a different canonical protocol hash than FitPlan.protocol_sha256 is also invalid
- With frozen protocol candidate_thresholds `[0.5,0.7,0.8,0.9,0.95]`, a 0.81 candidate is rejected
  before scoring. With its claim-support budget `{false_nudge_max:0.05,
  min_evaluable_coverage:0.9,min_justified_opportunities:20}`, an objective of 0.051, 0.89 or 19
  respectively is rejected. Equality is exact; the policy tolerance cannot relax those values
- Reuse a validated context after changing a candidate, objective or EvidenceRef: request-seal
  mismatch, rejected. A caller-supplied `protocol_validated:true` is an unknown field, never authority
- Fit a false-Noul candidate at threshold 0.8 against saved positive probability 0.2: core
  evaluates `1-p == 0.8` and abstains for rounding uncertainty. A fixture `>=` nudge is not an
  admissible fit result. Exact-fit scoring makes zero provider calls
- After a correlated stale-before-consume refusal, submit a matching NoAdviceResponse: record
  not_exposed, no delivery/acknowledgment credit, then recheck before a new generation. Submit
  that negative response after any possible exposure or with a fabricated refusal hash: reject
- Add `"advice":"Read ruling::engineering::reuse-before-reinvention"` to Wake: unknown field,
  reject before tool dispatch. The skill cannot append advice outside JSON either
- When spawn returns only `{"task_name":"/root/prove_native_child_boundary"}`, the valid
  Child is `{"agent_id":null,"task_name":"/root/prove_native_child_boundary"}`. Copying that
  name into agent_id is unsupported identity data and is rejected at enrollment. Null does not
  excuse a different task_name or authorize changing the enrolled identity
- Change only worker `child_attestation` to the expected child while actual origin is another
  child: `origin_mismatch`, invalidate; the attestation cannot override the tool result
- Reuse a valid consume after acceptance epoch changes, generation advances or selected revision
  changes: no advice with `epoch_mismatch`, `generation_mismatch` or `stale_revision`
- Submit `sequence: 3` after sequence 1, or claim idle without observing completed turn 2:
  `sequence_gap`/`stale_checkpoint`, never synthesize the missing boundary
- Call consume twice after the first committed but stdout was lost: `already_consumed` or
  `uncertain_delivery`; the result hash can be reconciled, the template is never emitted again
- Revoke between provider reservation and completion: preserve charged response, refuse reserve
  and consume with `permit_revoked`; no fallback ordinary advisory run
- Restart after the tenth of ten attempts was reserved: the eleventh is `budget_exhausted`, even
  if the tenth provider crashed before answering
- Put an `experimental_permit` object in `promotions`, or remove its non-null trace authority:

- Rename fixture-calibration output to the real calibration filename: tag, execution mapping,

- Count `wake_accepted` as delivered/acknowledged, or count acknowledged as observed_resolved:

- Stop the runner while a claimed wake lacks a result: preserve unknown state and spent budgets;

## 13. Implementation seams and verification obligations

Assign adapter/skill and core/permit work only after schema review. `src/cli/expert.rs` owns the
new explicit flags and native/pilot dispatch; `src/cli/mod.rs` retains its existing delegation.
`src/expert/pilot.rs` owns types/admission/accounting/clock checks;
`src/expert/calibration.rs` owns the pure saved-response fitter; `trace.rs` owns the existing
store lock, atomic ledger transaction, shared reserve gates, receipts and replay integration.
Keep one core revision/policy implementation. Python wraps the reviewed core and actual
model-side skill, with no fabricated native API. `adapters/systemone/provider.py` remains the
provider transport; the evaluator adds execution and provenance, not a second Kev client.

Required regressions target structured outcomes and actual paths: post-work per-binding
capture/rebuild on incompatible revisions; source-kind spoof fields rejected at ingestion;
raw/canonical protocol hashes, parsed plan/manifest equality, exact frozen threshold/objective
binding and stale-context seals; core saved-response fitting including false-Noul polarity, tolerance equality, Score tails,
paired expertise and wrong-target labels; observed no-advice completion versus unknown exposure;
unknown keys/tags; mismatched
origin/task/epoch/generation; absence of CAS; incomplete observed sequences; differing selected
revisions; before-provider permit refusal with zero dispatches; revoke during inference; delivery
reservation/consume budget races; duplicate consume; process failure before/after each durable
commit; incomplete stdout; lost host/worker receipts; restart and boot/UTC discontinuities;
missing/corrupt ledger; payload deletion; exact-replay identity; pilot-to-promotion rejection;
fixture-to-real-calibration rejection; off zero calls; shadow real calls/no advice; pending host

current repository contract obligations. It cannot establish this schema's semantic correctness,
actual capability, durability under crash, model quality or reduced owner steering.
