# Haiku handoff benchmark: four fresh sessions over one evolving project

**Preparation gate: frozen design for approval. No subject has run.** Everything below is built and validated in this directory; `manifest.json` is written by `controller.py freeze` and any deviation from it invalidates a run.

Research question: can BlaBla preserve correctness across repeated fresh-agent handoffs while reducing the project context and rediscovery work each new agent requires? Secondary hypotheses (not assumed): less total supplied context, less rereading, fewer turns and tools, fewer edit rounds, fewer self-authored tests, smaller change radius, fewer accumulated regressions.

## Critique of the proposal and the changes made

| Change | Why | Bias or confound removed |
| --- | --- | --- |
| Stage 1 is a numeric transient property (resonance) with a consumer action, not a second boolean flag | a flag with a gate is structurally a copy of quarantine; a generic "add a flag like the last one" pattern would solve it | the handoff test would measure pattern copying, not inherited project knowledge |
| Resonance is deliberately transient (not persisted) | the field an agent most plausibly persists "for safety" is exactly the rule Stage 3 (persistence refactor) and Stage 4 (recovery after restart) depend on | gives the later stages a real dependency on a subtle earlier rule (spec §22) |
| Stage 2 echo requires EQUAL phases, transfer requires different phases | the two rules are deliberately opposite | catches copying transfer's guard into echo; adds a second consumer of the quarantine transfer-in rule |
| Stage 3 refactor is scored by the existing behavior scorer plus an architecture shape check (`DURABLE_FIELDS`) | a refactor adds no behavior; the architecture scorer already fixes the five roles | Condition C gets no new contract here, so BlaBla's contribution is "no behavior change" evidence only; the structural intent stays outside BlaBla on purpose (spec §54) |
| Stage 4 recover resets phase to 0 without rotate's return cap | the restart-like reset is the mirror of the existing cap rule | a rule generic knowledge does not supply; interacts with quarantine parity and echo |
| Canonical seed chosen so that every stage reference reaches GREEN under the frozen profile (seed 2, 4096 actions) | seed 0 left the pre-existing `rotate-return-cap-preserves-quarantine` obligations unexercised at stage 2 and stage 4 within 4096 actions | a YELLOW that a correct implementation cannot clear would block completion for a correct C subject; a correct implementation reproduces the reference trajectory, an incorrect one cannot hide behind the seed |
| Subject tool timeout raised to 600 s for every condition | `blabla finish` takes 60 to 90 s at 4096 actions and Claude Code's default Bash timeout is 120 s; A/B pytest runs benefit equally | a harness timeout masquerading as a BlaBla failure |
| Stage-interleaved order A1 B1 C1, A2 B2 C2, ... | a provider or Claude Code change during the campaign lands on every condition | condition-specific environmental drift |
| Stage 3's refactor target is stated in the shared task text | BlaBla has no structure layer, so C cannot learn the refactor target from contracts; the behavioral constraint (nothing changes) is where the conditions differ | none; stating the target for all three is the only equal-intent option |
| Each stage lands the authoritative contracts for C and records any contract edit the previous subject made | the contract author is not the subject (spec §28); a weakened contract is a finding, not a repair | silent weakening surviving into the next stage |
| Per-viewer test files, stray files and `.blabla` records carry over unchanged between stages | branch continuity (spec §17); the controller removes only caches | cleaned handoffs would hide accumulated clutter |

Rejected: more stages, more models, weakening A or B, telling C contract filenames, resetting branches, repairing branches, a generic orchestration layer.

## 5. Chain mechanics

- Stage 1 of every condition starts from the frozen template (`prep/template`, or `prep/template-C`). Stage N+1 starts from the exact final tree of stage N of the same condition; only `__pycache__` and `.test-data` are removed.
- Condition C contract authority (owner correction, applied before freeze 2): `project.bla` and the active contracts are controller-owned inputs. Their hashes are recorded after landing (`started.json`) and after the subject (`contract-audit.json`, with a unified diff of every modified authoritative file and every added `.bla`). A subject edit is a contract-tampering / intent-drift event: it is recorded and scored, never carried forward. Before the next C stage the controller removes every non-authoritative `.bla` under `contracts/`, re-lands the authoritative set for the new stage, and preserves every application and other source change; the independent scorer and the diagnostic `finish` always use the controller-frozen contracts.
- Stage 3 interpretation (owner ruling): BlaBla may legitimately be GREEN when the refactor task begins; GREEN is behavioral completion only. The architecture scorer decides whether the refactor happened. `scoring.json` records `behavioral_green_but_refactor_missing` (diagnostic finish GREEN with architecture FAIL) and `subject_finish_green_while_architecture_fail`, the evidence for or against a future structure layer. No structure layer is added for this benchmark.
- Scorer failures are recorded, never repaired. A chain is BROKEN only when the application no longer answers `reset`/`observe` through the driver at preparation time; then `broken.json` is written and later stages of that condition are not run.
- Fresh model context every session: `claude -p` with `--no-session-persistence`; nothing but the prompt and the workspace.
- Order: A1, B1, C1, A2, B2, C2, A3, B3, C3, A4, B4, C4, sequential.

## 6. Scoring

Behavior: black-box pytest over the JSONL driver, `-rA` so every check id is recorded; per stage `SCORER_FILES[stage]` (Stage 1: core 42 + sealing 8 + quarantine 20 + resonance; Stage 2: + echo; Stage 3: as Stage 2; Stage 4: + recovery). Architecture: the bounded AST check with `resonance` protected, required operations by stage, and from Stage 3 the `DURABLE_FIELDS` shape. Drift per stage: regressions introduced (old checks failing now that passed before), recovered, remaining, and new-feature failures. Completion claim: final text classified, and for C the last `finish`/`run` outcome and gate. Validation: `prep/validation/validation.json` (each stage's reference GREEN under the profile and PASS; the previous stage's reference FAILS the new checks; one mutation per stage RED with a counterexample and scorer FAIL).

## 9. Cost estimate

The single-feature runs cost $0.377 to $0.438 and 4 to 6 minutes each at 44 to 57 turns. Twelve sessions at $0.35 to $0.60 each: about $5 to $7 and 60 to 80 minutes of subject time, plus about 25 minutes of preparation, scoring and diagnostic campaigns (each canonical campaign 60 to 90 s). Caps: $10 per session, $40 total.

## Run procedure (after approval)

```powershell
python artifacts/handoff-benchmark/controller.py freeze
foreach ($stage in 1..4) { foreach ($condition in "A","B","C") {
  python artifacts/handoff-benchmark/controller.py prepare --condition $condition --stage $stage
  python artifacts/handoff-benchmark/controller.py run     --condition $condition --stage $stage
  python artifacts/handoff-benchmark/controller.py measure --condition $condition --stage $stage
  python artifacts/handoff-benchmark/controller.py score   --condition $condition --stage $stage
} }
python artifacts/handoff-benchmark/controller.py report
```

The controller prepares, invokes, records and scores; it never suggests fixes, points at files, repairs output or interprets BlaBla for the subject. `prepare` refuses to reuse a run directory, verifies every hash against the manifest and refuses a prompt that differs from the frozen one; `run` refuses a changed controller or workspace and the total budget.

## Threats to validity

One run per cell: raw values, no statistical claim. The same author wrote contracts, A prose and B summaries; the cross-reference table is the equal-intent audit. B's maintenance cost is reported as bytes and diff lines only. C's repository carries the previous record, so its status line may name a stale GREEN, YELLOW or RED from the previous subject; that is the handoff state, measured. Windows only.

## Condition C under BlaBla v0.4.2 (`manifest-C.json`)

Condition C runs fresh from the Stage-0 template under the v0.4.2 binary, whose runtime semantics are self-describing (`blabla explain runtime::restart`, `Depends on:` in rule explain, `Runtime primitives used:` in status). `python controller.py templates --condition C` rebuilds `prep/template-C-v042` and refuses it unless every file hash equals the frozen `template_c_sha256` of `manifest.json` (the generated AGENTS.md block is byte-identical to `packages/C-AGENTS.md`); `validate --validation-dir validation-v042` repeats the reference, previous-reference and mutation checks under the new binary; `freeze --condition C` writes `manifest-C.json` and refuses to freeze if anything but the binary and the controller hash differs from `manifest.json` (`unchanged_from_baseline` records the comparison of contracts, references, packages, requirements, architecture, scorers, scorer files, canonical profile, template, model settings, C prompts and Python). C runs live under `runs/C-v042/stage-N`; A and B artifacts, `manifest.json`, `results.md` and `results.json` are untouched. `prep/campaign-C-v042.py` runs C1 to C4 strictly sequentially: each stage is prepared, run, measured and scored before the next is prepared. `report` writes `results-v042.md` and `results-v042.json` from the A and B rows under `runs/` and the C rows under `runs/C-v042`.

Additional C measurements (`metrics.json` `runtime_discovery` and `disclosure`, `scoring.json` `runtime_semantics`): the rules whose explain output showed `Depends on:`, whether `blabla explain runtime::restart` was called, which surfaces showed `runtime::` and the first turn, tool index and second at which it became visible; whether the subject used status only, which rules and primitives it explained, which full contracts it opened through Read or a shell read, whether it opened `persistence.bla`, and which project documents it read; on the final workspace, the status of every restart-dependent obligation under the frozen profile, application lines added that mention restart, and whether a `"restart"` action was handled by the application (a trusted restart is never an application command).
